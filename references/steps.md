# 手順の本文（SKILL.md の地図の各手順の中身）

SKILL.md には地図と決まりだけを置き、手順の中身はここにある。**今やる手順の節だけを読む**：
`python <skill>/scripts/guide.py steps 2`（「2.」で始まる節）・`guide.py steps 資料の受け取り`・`guide.py steps 原稿のモード`。

## 資料の受け取り（発表も講座も同じ）

ユーザーは資料を**スライドを作るフォルダの一番上**に入れて、「入れたから、〇〇で作って」と頼む。AI がそれを**資料置き場**に格納する。
発表フォルダは一番上の `<資料名>/`（講座は `<講座名>/`）で、資料置き場はその中の `資料/`。できたスライドと原稿のページも発表フォルダに置く。

1. **中身を確かめてから写す**：まず `python <skill>/scripts/materials.py --scan <スライドを作るフォルダ>` で、一番上の資料らしいファイルと中身の手がかり
   （PDF の頁数と最初の行・pptx の枚数と最初の文字・画像の大きさ）を見る。この発表に使うものを決め（ユーザーがファイル名を言ったらそれ、言わなければ
   手がかりから選んで「これを使います」と返答に書く。関係のなさそうなものは使わない）、`materials.py <発表フォルダ> --collect ファイル名 ...` で写す。
   **元のファイルは消さない**（コピー）。画像 → `図/`、前の発表の pptx → `過去のスライド/`、論文・教科書・要旨・メモ → `その他/`
2. **資料がそろっている発表と講座**（論文・教科書の節・講義録）：`materials.py <発表フォルダ> --source` で ✔ を見て、手順1（資料を読む）へ
3. **資料が全部はそろっていない発表**（学会・卒論発表・研究室の報告など。結果の図・過去のスライド・メモだけのことが多い）：
   - `materials.py <発表フォルダ>` が、`資料/方針.md` の必須の3節（**目的・結果（図ごとに何が見えるか）・結論**）と、図の有無を確かめる
   - **必須の3つは、ファイルに無ければチャットで聞く**：項目を並べて1回で聞く（「この発表の目的・各図で見えること・いちばん言いたい結論を、
     箇条書きでかまわないので送ってください」）。答えは**聞いた言葉のまま** `方針.md` に書く（言い換えて事実を足さない）。ファイルにあるなら、その場所を書く
   - **背景・方法は聞かずに下書きする**：過去のスライド・要旨・論文から AI が `方針.md` に下書きし、構成案と一緒に見せて直してもらう。資料に手がかりが無いときだけ聞く
   - 過去のスライドは `materials.py <発表フォルダ> --text` で文字を書き出して読む（pptx を開かない）。使う枚・使わない枚・古い結論は、方針.md の「過去のスライドの使い方」で聞く
   - **✘ が消えるまで先へ進まない**（構成案を作らない）。△（説明の無い図）は、その図で何が見えるかを聞く
   - 事実の扱い：結果と数値は、ユーザーの資料（図・方針.md・過去のスライド）からだけ取る。背景の一般論を足すなら、出典を付けるか ※（資料外の補足）。分からないことは推測で埋めずに聞く

## 0. 聞き手と設定の一覧（最初に）

設定は**デッキごとの一覧**に置く（ゼミ＝outline.md 冒頭の `## オプション`、講座＝講座の README の「学習者とゴール」と各回の設計メモの1節）。
スキル全体の共通プロフィールは作らない（個人の情報をスキルにも作業フォルダの共通ファイルにも置かない）。

0. **新しいデッキ・講座を始めるときと、「環境を確かめて」と言われたとき**は、`python <skill>/scripts/check_env.py` を走らせる
   （作業ディレクトリに `.venv` があれば、その Python で）。全部そろっていれば一言で済ませて進む。足りないときだけ、表を見せて次のとおりにする
   - **Python の部品が足りないとき**：【質問】で1回だけ聞く。「スライド作りに要る部品（<足りない名前>）が入っていません。
     この作業フォルダに仮想環境 `.venv` を作って、インターネットから入れてよいですか（数分。PC 全体には入れません）」。
     選択肢は「入れる（おすすめ）」「自分で入れる（コマンドを見せる）」「やめる」。許可が出たら、`.venv` が無ければ `python -m venv .venv`、
     続けて `.venv/Scripts/python -m pip install -r <skill>/requirements.txt`（Mac・Linux は `.venv/bin/python`。`uv` が入っていれば `uv venv --seed .venv` と `uv pip install --python <その python> -r ...` のほうが速い）、終わったら同じ Python で check_env をもう一度走らせ、そろったことを確かめてから進む。
     通信を止める道具（サンドボックス）では、この2つのコマンドだけ外で動かす許可を求める。許可が無いうちは入れない
   - **PC 全体に入るもの**（Python 本体が無い・古い、PowerPoint も LibreOffice も無い、日本語フォントが無い）：作る前に伝え、表のコマンドを見せて**ユーザーに入れてもらう**
     （「入れて」と頼まれたときだけ、確認を出してから動かす）。PowerPoint も LibreOffice も無いだけなら、**聞かずに pptx だけで進める**（`make_deck.py <work> --no-render`）。渡すときに、検査をしていないことと、LibreOffice を入れればあとから検査できることを伝える
1. **必須を聞く**（新しいデッキ・新しい講座を始めるとき）：必須は**聞き手のテーマへの詳しさ**だけ。依頼文で分からなければ【質問】で聞く
   - 初学者／多少知っている／かなり知っている（講座では学習者＝ふつうはユーザー本人、発表では聞き手）
   - 同じ質問の中で、任意の**発表時間**（発表なら。15分／20分／30分／決まっていない）も聞いてよい。答えが無ければ空のまま進める（枚数は資料と話の量で決める）
   - **丁寧さ**は詳しさから決める（初学者 0・多少知っている 1・かなり知っている 2。推論距離のつまみ、outline-review.md）。ユーザーが変えたいと言えば変える。講座でも回ごとに変えてよい
2. **資料があればもらう**（任意。必須のあと、プロフィールを勧める前に。既定は「なし」）：先に一度、`python <skill>/scripts/materials.py --scan <スライドを作るフォルダ>` で、
   一番上にもう資料が入っていないかと、その中身の手がかり（頁数・最初の行・枚数）を見る。あれば「〇〇.pdf（12頁、題「…」）が入っています。これを使いますか」と同じ質問の中で確かめる。無ければ「スライドに使う資料（論文・教科書の PDF、結果の図、前の発表のスライド、メモ）が
   あれば、このフォルダの一番上に入れて教えてください。無ければテーマだけから作ります」。入れたと言われたら「資料の受け取り」で格納する。
   無ければ一覧の「資料」は「なし」のまま進め、事実は出典で確かめる（講座のテーマだけのときと同じ）
3. **任意のプロフィールを勧める**（資料のあと、同じ返答の中か、すぐ後の一言で）：「聞き手（講座ならあなた）の専門・研究テーマ・よく知っていることを書いてもらえると、
   知らない言葉の言い換えと、止まる所の判定がよくなります（任意）」。答えてもらえたら一覧の「聞き手のプロフィール」に書く。無ければ詳しさだけで進める
4. **一覧を見せる**：決まった値を渡して表を作り、**そのまま返答に貼る**。「必須の抜け」と出たら、聞いて埋めるまで先へ進まない
   ```bash
   python <skill>/scripts/slide_profile.py --table --set 聞き手のテーマへの詳しさ=多少知っている --set 発表時間=20
   python <skill>/scripts/slide_profile.py --table --kind 講座 --set 聞き手のテーマへの詳しさ=初学者
   ```
5. **書く**：ゼミは outline.md 冒頭の `## オプション` に表の全部を、講座は README の「学習者とゴール」（テーマへの詳しさ・学習者のプロフィール）と、
   各回の設計メモの1節（聞き手のテーマへの詳しさ・聞き手の前提知識・丁寧さ）に。**聞き手の前提知識**（知っている＝…／知らない＝…）は、
   詳しさとプロフィールから AI が書く（「知っている」側は推論距離の穴に数えない）
- `check_outline.py`・`check_memo.py` は、必須（聞き手のテーマへの詳しさと、そこから書く聞き手の前提知識）が無ければ ✘ にする。発表時間・資料・プロフィールは任意。✘ のまま構成案のレビューや図に進まない
- 途中で「オプションを見せて」「設定を確認したい」と言われたら、今の値で表を出し直す（outline.md の値を `--set` で渡す）
- 質問回答デッキ（手順8）や、続きもので前の回がある場合は、前の回の値を使い、表を貼るだけで質問は省く

| オプション | 決める場所 | 既定 | 効くところ |
|---|---|---|---|
| 聞き手のテーマへの詳しさ | **必須**。最初の【質問】 | — | 丁寧さ（初学者 0・多少知っている 1・かなり知っている 2）と、聞き手の前提知識の書き方 |
| 聞き手の前提知識 | **必須**。詳しさとプロフィールから AI が書く | — | 推論距離の監査（「知っている」側は穴に数えない。outline-review.md） |
| 聞き手のプロフィール | 任意。最初の【質問】で勧める | なし | 原稿の橋渡し（知らない手法を聞き手の分野の言葉で言い換える）、前提知識の精度、議論のスライド |
| 発表者名 | 任意（ゼミ） | なし | 表紙（`slide_profile.author`） |
| 原稿のモード | 依頼 | 発表（講座は AI講義） | 手順6（発表モード／AI講義モード） |
| 発表時間 | 任意（最初の質問で聞いてよい） | — | 原稿の長さの合計と枚数の目安。無ければ資料と話の量で決める |
| 枚数の目安 | 依頼で上書き | 発表時間÷1.5〜2分 | 本文スライドの枚数（表紙・区切りを除く）。資料が多ければ範囲を絞って収める。外れたときは `check_outline.py` が知らせる |
| 枚数が少ないとき | 依頼 | 足さない（短くてよい） | **枚数合わせに内容を足さない**。少ないときは抜けている話（前提・図の読み方・結果の論理・聞き手が引っかかる所）を見直し、それでも少ないなら outline.md に「枚数の理由：…」。「説明を厚くする」のときだけ背景・図の読み方・結果の論理を足す。推論距離の橋は枚数と関係なく入れる |
| 丁寧さ | 詳しさから（変えてよい） | 初学者 0・多少知っている 1・かなり知っている 2 | 推論距離のつまみ：1枚に許す要3（あとの枚・確認問題・回のゴールや話の筋で使う前提）の数。要1（この枚の結論のなぜ）と要2（名前の付いた知らない語）はいつも架ける |
| 答えの位置 | 依頼 → 一覧の「答えの位置」 | 発表は先・講座は後 | 先＝問いのすぐ後で答え（主張）を言い、あとの枚で根拠（Minto のピラミッド原則の結論から）。後＝前で問いを立て、後ろ3分の1で答えを回収。`references/story.md` 1節 |
| 範囲 | 依頼 | 全部の結果 | 「主要な結果」なら構成案で残す図を選び、残りは1枚にまとめるか原稿で触れる |
| 議論のスライド | 依頼 | 入れない | 入れるなら考察の後に1枚：疑問点・限界・発表者の研究との関係（資料外は明記） |
| 構成案の確認 | 依頼 | 見せる | 手順2の最後。「任せる」なら見せずに完成まで進め、渡すときに構成の要点を添える |
| 出力先 | 依頼 | 作業フォルダの一番上 | スライドと原稿のページを置くフォルダ |
| テンプレート | 依頼（名前）→ 一覧の「テンプレート」 | テンプレート1 | 同梱の テンプレート1〜8（構造が違う。番号は見やすさの順。構造の名前「結論の囲み」などでも選べる）と、追加したもの（`スライドテンプレート/テンプレート一覧.md`）。`deck_options(P, name=..., color=...)` に渡す |
| 色 | 依頼（色の名前）→ 一覧の「色」 | テンプレートの標準の色 | 配色の名前（`assets/templates/配色.json`：青・紺とオレンジ・生成りと山吹・藍・青緑・珊瑚・墨と山吹・深緑・グレーと赤・墨と藍） |

**テンプレートを選ぶ**（「テンプレートは〇〇で」「色は〇〇で」）：名前を `deck_options(P, name="〇〇", color="深緑")` に渡す。
どれがあるかは `slide_profile.py --table` の「テンプレート」の行と `assets/templates/` で見て、名前の一覧を見せる。決めた名前は、そのデッキの一覧の「テンプレート」の行に書く。
見本を組む・新しいテンプレートを作るときは `references/templates.md`。

## 1. 資料を読む（全部読む）

```bash
python <skill>/scripts/pdf_pages.py extract "<発表フォルダ>/資料/その他/資料.pdf" <work>/src
```

- 見開きスキャンの書き出しは1ページ数十秒かかる。2分を超えそうならバックグラウンドで実行する。
- **ページ画像ができたらすぐ、構成案レビュー担当の【別のエージェント】を起動して資料を先読みさせる**
  （`references/outline-review.md` の「A. 先読みの依頼」、バックグラウンド）。構成案ができてからの待ち時間が短くなる。
- 教科書はスキャン（テキスト層なし）で、A4横の見開き。`pNN_L.png` / `pNN_R.png` を【画像を見る】で1枚ずつ見て読む。
  頁番号・節の始まりと終わり（次の節の見出し）を確認し、担当範囲だけを扱う。前の節の末尾が混ざっていることが多い。
- 論文PDFはテキスト層があるので `pNN.txt` を読み、図は `pNN.png` を見る。
- Markdown・テキストの講義メモやノートは、そのまま読む（ページ画像にしない。`src/` も作らない）。
- 読みながら、段落ごとに「何を主張しているか」「式」「数値」「図」をメモする。数値・式・固有名詞は資料のとおりに写す。

## 2. 構成案（outline.md）を先に作る — 中身はまだ作らない

**どのスライドにどの内容を入れるかを全部決めてから、本文・図・ビルドに進む。** 1枚ずつ作りながら考えると、
内容の重複・抜け・1枚への詰め込みが起き、青帯も本文の要約になってしまう。

`<work>/outline.md` に、全スライドを1行ずつ表にする（見本：`examples/zemi/outline.md`。教科書の輪読も同じ列で、「タイトル」列は省く）。論文のときは「タイトル」列（背景／実験手法／実験方法／結果①②③／考察）を足し、
流れ・表紙・図の置き方は style-guide 5節「論文紹介」に合わせる。

| 列 | 書くこと |
|---|---|
| 番号 | スライド番号 |
| 範囲 | 教科書の頁・段落（論文なら節・図番号） |
| ●見出し | トピック（10〜15字） |
| 前の枚から | 前の本文の枚の青帯から、どうつながるかを「語（種類）」で：そして（並べる・詳しく・次へ）・しかし（壁・意外・疑い・限り）・だから（帰結・手段・問い）。本文の最初の枚は「—」。「そして」は4つ続けない、「しかし」は1つは要る、しかし（壁・疑い）のあとには越え方・確かめ方の「だから」（`references/story.md` 2節の表に、種類ごとの青帯と原稿の1文目の書き方） |
| 青帯（結論） | そのスライドで聞き手に持ち帰ってほしい一文（全角15〜26字、句点なし）。**役割が本文の枚では空にしない**：言い切れない枚（目的・手順など）は、その枚の要約の一文にする。本文以外の役割の枚は「—」にする（組むときに帯も●も無い枚になる） |
| 図で見せるもの | テーマか難所のどちらを、どんな図で（figures.md 1節）。**「目的：種類：中身」で書く**（先に目的を選び、その目的のおすすめの種類から図を選ぶ。例「比べる：棒グラフ：…」。目的と種類の表は figures.md 1b）。本文の枚で「なし」にしない |
| 本文の要点 | **本文の形の入れる所の書き方で**（展開なら `左 → 右`、問いなら `〜？⇒ 結果`、ラベルなら `見出し：説明`。`references/structures.md` 1節の「入れる所」）。**3〜4個**（結論の根拠・数値・具体例・よくある間違い）。赤字にする結論に★（scaffold.py が赤字にする）。2個以下の行が半分を超えると check_outline・check_memo が ✘。**数値・例の要点には出どころを〔…〕で**（〔II. Observation〕〔Fig. 2〕〔要旨〕〔p.12〕、講座は〔事実3〕＝3節の表の行、自分の計算は〔発表者の概算〕）。カードがその所を書き手に渡すので、書き手が探さずに数値を引ける。無ければ △ |
| 本文の形 | 文字の組み方（帰結・ラベル・展開・縦の結論・場合分け・問い・手順・式の注釈・箇条。2つなら「ラベル・帰結」）。`references/structures.md` で内容に合う形を選ぶ。設定の一覧に「本文の形の割合」があれば、その割合に寄せる。同じ形の組は4枚まで。結論が上にある構造（結論ヘッダー・結論タイトル・細い左帯と副題）では帰結を避ける（使うテンプレートに合う形は structures.md の3節）。全面の図・大きな数字だけの枚は「—」 |
| ノートへ | スライドには載せず口頭・ノートで補う細部 |
| 役割 | **必ず書く。次の語から選ぶ**：表紙・本文・区切り・目次・確認問題・解答・参考文献・謝辞・質問待機（発表の最後に質問を待つあいだ映す枚。想定質問は下の「想定質問」の枚。聞かれそうな質問に答える予備の枚は、中身があるので本文）。結論の一文を置くのは本文だけ |

決める順番（**上から**：筋 → 青帯 → 本文の形と図（何をどう伝えるか）→ 要点と出どころ。資料は手順1で読み終えているので、ここでは資料の順に割り振る前に、まず言いたいことを決める）
0. **話の筋を先に書く**：表の前に `## 話の筋` の表（状況・複雑化・問い・答え。状況は聞き手が今知っていること、問いは疑問の形で前のほうの枚、
   答えはこのデッキの主張の一文で、置く枚は一覧の「答えの位置」に合わせる：**先**（発表の既定）＝問いの枚かそのすぐ後で答えを言い、図は答えを支える柱の一覧、
   最後の本文の枚で言い直す／**後**＝後ろ3分の1で回収）。論文なら、研究者が何に困り、どこで壁に当たり、どう越えたか（語り手）。`references/story.md`
1. 担当範囲を段落ごとに区切り、1枚1トピック（1メッセージ）で割り振る。教科書の輪読なら段落1つで1枚が基本
   （教科書1ページ≒2〜3枚）。最後に節の総括（まとめの図など）があればそれで締める
2. 各スライドの**青帯の一文を先に決める**。本文と図はこの一文を支えるためにある。青帯は筋に沿わせ、前の枚からのつながりを「前の枚から」に「しかし（壁）」のように書く。
   「そして」が4つ続く所は、「なぜこれが要るか」（だから）か「これでは足りない」（しかし）でつなぎ直すか、まとめる
3. 青帯の一文に合わせて、まず**本文の形と図で見せるもの**（その一文を、どの形・どの図で伝えるか）を決め、そのあとで形が求める**本文の要点**（比較なら比べる2つの値、場合分けなら分かれ目の条件）と出どころ、ノートに回す細部を決める
4. outline.md の冒頭の `## オプション`（手順0）に、聞き手の前提知識（知っている／知らない）と丁寧さが入っていることを確かめる
   （レビューの推論距離の監査が前提にする。丁寧さ＝1枚に許す要3（あとの枚・確認問題・回のゴールや話の筋で使う前提）の数。要1・要2はいつも架ける）
   書くときから穴を避ける：その枚の結論の「なぜ・どうやって」をその枚に書く（次の枚で説明するなら予告）、知らない側の名前の付いた法則・用語は初出で一言の意味、
   数値には物差し、「変化なし」には「⇒ 何が言えるか」（outline-review.md「書くときから避ける」）

5. **想定質問**（発表だけ。講座は確認問題がある）：発表のあと聞かれそうな質問を **4問**、表の後ろに `## 想定質問` の表で書く
   （`| 番号 | 型 | 質問 | 回答の要点 | 戻る枚 |`。番号は Q1〜Q4、型は 疑い・なぜ・数値の意味・限界・今後・使い道 から1つ（先に型を選んでから質問を書く。4問で2種類以上、できれば3種類）、戻る枚＝答えるときに戻ると説明しやすい本文の枚の番号）。
   構成の表の最後に、役割「想定質問」の行を **2枚**（1枚に2組）足す。scaffold.py が `s.qa_pairs(...)` で質問と回答の要点を並べ、
   カードが戻る枚とその青帯を書き手に渡す。**戻る枚はスライドに書かず、原稿で**「詳しくは N枚目に戻ると…」と言う。check_outline が数を確かめる（△）。
   選び方：疑い（雑音・別の説明ではないのか）、仕組みの「なぜ」、数値の意味、限界・今後、を混ぜる。答えは構成案の事実だけで言えるものにする

構成案のチェック（ここで直すのが一番安い）
- [ ] 青帯の一文だけを上から順に読むと、節の話の流れが通じる。筋の問いが前のほうで立ち、答えが「答えの位置」どおりの枚にある（先なら問いのすぐ後、後なら山場を越えた後ろのほう）
- [ ] 教科書の段落・式・図がどれか1枚に割り当たっている（抜けがない）、同じ話が2枚に出ていない
- [ ] 1枚の要点が4個を超えていない（超えるなら分ける）
- [ ] 図がテーマか難所の理解を確かに助ける（飾りになっていない）
- [ ] 「変化なし」の結果には「⇒ 何が言えるか」が続く。（論文）考察に「示していないこと」がある

迷った所（資料の読み方・どちらの形にするか決めきれなかった所）は、outline.md の末尾の `## 迷った所` に1行ずつ書く（レビューのあとの直しを、新しい担当がするため）。

**構成案ができたら `python <skill>/scripts/check_outline.py <work>/outline.md` を走らせ、✘ を直す**（△ は直すか、出力の言うとおり理由を書く。基準と直し方は出力にある）。中身を作ってからでは直しにくい。

**構成案ができたら、【別のエージェント】にレビューさせる（必須）。** 手順とプロンプトは `references/outline-review.md`。
小さな依頼なら冒頭の分岐のとおり省略してよい（上のチェックリストを自分で当てる）。
- 手順1で先読みさせておいた担当に、【続けて頼む】で「B. レビューの依頼」を送る
- **レビューの結果はそのまま `<work>/outline_review.md` に残す**
- 「必ず直す点」は資料で確かめてから outline.md に反映し、「直すとよい点」は採否を判断する
- 推論距離（専門外の聞き手の引っかかり）は、妥当なものを選び、説明を別に足すのではなく流れの中で答えが出るように構成案を直す。
  採ったもの・採らなかったものを outline.md の `## 引っかかりへの手当て` に `- [番号]` で残す（やり方は outline-review.md「推論距離（専門外の引っかかり）の扱い」）。
  **原稿に回す手当ては、原稿で言うことを「…」で書いておく**（渡す前の確認が、原稿にその言い回しがあるかを見る）
- 直したら `check_outline.py` をもう一度走らせる

**レビューを反映した構成案をユーザーに見せて OK をもらってから**本文・図・ビルドに進む
（表をそのまま、または青帯と図の列だけを示し、レビューの判定と直した点を2〜3行で添える）。
ユーザーが「一気に作って」「任せる」と言っている場合は見せずに進めてよい（レビューは省かない）。

## 3. 図を用意する

**図のファイル名は `figs/sNN.png`（NN はスライド番号。1枚に2つなら `sNN_b.png`）**：カードと骨組みがこの名前を使うので、図と本文を別々に進められる。

描き始める前に **`references/figures.md` を読み、`references/figure-style-examples.jpg` を【画像を見る】で見る**
（小さな依頼なら figures.md の 1・2節だけでよい）。
方針は「模式図として伝わりやすさ優先。立体は可だが、濃い陰影・光沢・グロー・グラデーション・くどい太線はなし」で、見本の図の質感が基準。

- **図の文字は 14pt が基本（12pt は最小）、1つの図にラベルは5個まで、ラベルは名詞だけ、描いた幅のまま置く**（`s.image(path, x, y)` と幅を渡さない。`w=` で広げると図の文字が本文と同じ大きさになる。figures.md 2節「文字」）
- **図は必ず `<work>/figs.py` に描き、`figkit` の `save` で保存する**（`savefig` を直接呼ぶ・PIL で描く・別名のスクリプトで描くのは不可。`save` が文字の大きさ・ラベルの数・線との重なりを WARN で知らせるので、残っていたら直す）
- 図スクリプトは `def f_<名前>()` を並べ、`python figs.py <名前> ...` で一部だけ再生成できる形にする（引数は関数名の `f_` を除いた部分。例 `examples/zemi/figs.py`）
- **スライドの型を内容で選ぶ**（左に文・右に図／上に文・下に横長の図／全面の図／2つを並べて比べる／大きな数字・結論／表／流れ図／図解の型）。部品と名前は `references/structures.md`。同じ型は4枚まで
- **描く前に、これまでの図と型を確認する**：`python <skill>/scripts/catalog.py _work _work/figure-catalog`（`_work` がまだ無いときは飛ばす）。同じ話題・形の図があれば、その figs.py の関数を流用する。よく使う形は `figlib.py` の型（figures.md 4b節）
- 図がない話題は `figkit.py`（部品）と `figlib.py`（型）で描く。何を図にするか・種類の選び方・レシピは figures.md の 1, 1b, 4, 4b 節
- 箱と矢印だけの流れ図は、画像ではなく `s.flow([...])`（PowerPointの図形、後で編集できる）で置く
- 形は式から計算して物理的に正しく、数値は資料にある値か確かな値だけ。教科書外の値・概略図には `s.caption(box, "（概略）")`
- 教科書の図：`python <skill>/scripts/pdf_pages.py crop <work>/src/p05_L.png <work>/figs/fig7_14.png --box x0 y0 x1 y1`
  （表示した画像の座標から元画像のピクセルへ換算する）。切り出し結果は必ず【画像を見る】で確認
- 論文・教科書の図は**そのスライドで話すパネルだけ**を切り出す。読み方の注記（`s.note`・`s.pointer`・`s.oval`）を重ねてよい（style-guide 5節「論文の図の扱い」）
- **論文・教科書から切り出した図には、必ず出典を付ける**：`s.caption(b, "（Otani et al., Sci. Adv. 2025, Fig. 2）")`。教科書は「（書名 図7.14）」。描き直したときは「（… Fig. 2 をもとに作図）」
- 論文・教科書の図を含むデッキは、ゼミと自分の勉強のためのもの。ユーザーが外に配る（ネット・学会・会社）と言ったら、論文のライセンス（CC BY など）か出版社の許可を確かめるよう一言伝える
- 描いたら・直したら `python <skill>/scripts/figgrid.py <work>/figs <work>/render/figs_grid.jpg [名前...]` で一覧にして目視し、figures.md 5節のチェックリストで確認する（ラベルと線の重なりが一番多い）

## 4. ビルドスクリプトを書いて生成する

**1枚ずつ書く**：`cards/NN.md`（scaffold.py が作る）を読み、そのカードと資料の範囲だけで `parts/NN.py`（その枚のコード）と `parts/NN.md`（その枚の原稿）を書き、全部そろったら `scaffold.py <work> --merge` で build.py・notes.md に戻す（青帯を変えた枚は戻らない。構成案を直すか、その枚を書き直させる）。
`<work>/build.py` に、outline.md の行をそのまま1枚ずつコードにする（青帯 → `summary`、●見出し → `heading`、
本文の要点 → 本文の形の部品（帰結 `s.lead`・ラベル `s.block`・展開 `s.develop`・縦の結論 `s.lead_down`・場合分け `s.cases`・問い `s.ask`・手順 `s.numbered`、箇条は `s.p`）、ノートへ → `s.notes(...)`）。**本文の形は部品で組む**（`s.p` で同じ見た目を手で作らない。渡す前の確認が部品の名前で構成案と突き合わせる）。作りながら内容を足し引きしたくなったら、先に outline.md を直す。

```python
import sys; sys.path.insert(0, r"<skill>/scripts")
from zemi import Deck, Eq, C, title_right_edge

T = "3.2 熱力学温度"
from slide_profile import load_profile, author, deck_options
P = load_profile(HERE)                 # 作業フォルダの outline.md（講座は memo.md）の設定の一覧と、追加したテンプレート（手順0）
AUTHOR = author(P)                     # 表紙の発表者名
deck = Deck(workdir="build", **deck_options(P))   # テンプレートと使うレイアウトと色（一覧の「テンプレート」「色」。名前で選ぶなら name="テンプレート3", color="深緑"）
A = deck.area                          # 本文の場所（構造ごとに違う：x・top・right・bottom・fig_x。柱のある構造は text_right まで）。位置はこれから決める
deck.title_slide([T], author=AUTHOR)

s = deck.slide(T, summary="熱力学温度はカルノー・サイクルの熱量比で定義")
s.heading("熱力学温度（ケルビン目盛）")
s.at(1.0, 1.95)                                    # 本文の流し込み開始位置
s.p("理想熱機関（カルノー・サイクル）で\n出入りする熱量に基づく", gap=0.12)
e = s.peq(r"\dfrac{T_1}{T_2}=\dfrac{Q_1}{Q_2}")    # 数式（行として置く）
s.defs(e.right + 0.4, e.y, [("T", "熱浴の温度"), ("Q", "出入りする熱量")])   # 数式の右に変数の定義を縦に（記号は斜体、「：」区切り）
s.prow(["定点：", Eq(r"T=273.16\ \mathrm{K}"), "（水の三重点）"])   # 文章と数式を1行に
s.p("{r:作業物質によらない絶対温度目盛}")          # 赤字
s.arrow(5.2, 3.0)                                   # 水色のブロック矢印（direction="down" も可）
b = s.image("figs/carnot.png", x=7.6, y=1.25, w=5.0)
s.caption(b, "（概略）")                            # 図の右下に小さな注記
s.oval(b.x + 1.9, b.y + 0.3, 0.55, 0.5)             # 図の注目点に重ねる赤い輪（塗りなし）
s.note(b.right + 0.5, b.y + 1.2, "実測の [012]", color=C.RED)   # 論文・教科書の図に重ねる読み方のラベル（白抜き16pt、名詞だけ）
s.pointer(b.right + 0.45, b.y + 1.37, b.right - 0.03, b.y + 1.37)  # ラベルから注目点への矢印（補助線は head=False, dash=True）
s.notes("発表で話す内容（2〜4文）")

# 比較表（薄青の見出し行＋薄灰のセル。青帯と同じ濃い青では塗らない）。rows = [(行ラベル, [セル...])]
# 列幅は全列共通（1.65）か、列ごとのリスト（[1.45, 2.95]）。長い説明の列だけ広げたいときはリストで
s = deck.slide(T, summary="…")
s.table(8.3, 1.85, 1.65, 1.0, ["方法A", "方法B"],
        [("精度", ["よい", "ふつう"]), ("手間の\nかかり方", ["大きい", "小さい"])], label_w=1.15)
deck.save("../教科書_3.2_スライド.pptx", title=T, author=AUTHOR)
```

マークアップ: `{r:赤}` `{u:下線}` `{ru:赤＋下線}` `{b:太字}` `{i:変数}` `{c:青}` `^{上付き}` `_{下付き}`、改行は `\n`。
数式は matplotlib mathtext（LaTeXのサブセット）。分数は `\dfrac`、`\oint` は自動でSTIXフォントに切り替わる。

**書くときの目安**（style-guide 3節。手順5の一覧がこれと比べる）
- **文字量は1枚あたり本文 100〜150字**（要点3〜4個に、根拠の数値か具体例を1つ。結論の語句か、決め手の短い一文（全角20字まで）を1か所赤字に。場合分け・2つ並べた・展開（前 → 後）の枚は、塊ごとに1文で2か所まで）。70字未満（図が主役の枚は50字未満）は少なすぎ、本文の枚の中央値が100字未満ならデッキ全体が薄い（check_layout が WARN）。180字・10行を超えたら目安超え、210字・12行が上限。**字数合わせの行で埋めない**：見出しや結論の言い換え・「〜の見方」「別々の要因」のような中身の無い句は、字数に入っても中身ではない。足すのは数値・具体例・よくある間違い・図の読み方。読みやすさは字数より、18pt 以上・1行20〜25字・塊（ラベル＋説明）に分けることで保つ。教科書の細部はスライドに詰めず、発表者ノートに書く
- 本文は自動で折り返さないので、自分で `\n` を入れる：1行は図の横で全角18〜20字、図がなければ25字まで
- 本文と図の間は 0.4 in 以上あける
- **本文は体言止めの短い句で書く（文章にしない）。** 「〜できない」「合っています。正確には〜」のような文章調は読み上げ原稿（notes.md）の文体。
  質問への回答や講義録の説明をそのまま写すと文章調になりやすいので、書いたら行末を見る：動詞・助動詞・「。」で終わる行は名詞句に切り直す（style-guide 3節「文の形」）

**発表者ノートは「読み上げ原稿」として書く**。
`<work>/notes.md` に「## スライド番号」ごとに書き、build.py の保存直前に読み込んでノートにする
（`from set_notes import load_notes`。build.py の `s.notes(...)` は作業メモ扱いで、notes.md があればそちらが優先）。
できあがった pptx に入れ直すだけなら `python <skill>/scripts/set_notes.py "<資料名>_スライド.pptx" <work>/notes.md`。

### 原稿のモード（誰が誰に話すか）

原稿のモードは2つ。

| モード | 話し手 → 聞き手 | 書き方 | 見本 |
|---|---|---|---|
| **発表モード**（デフォルト） | 依頼者のユーザー（発表者）→ ゼミ・発表の聞き手 | 「〜を担当します」で始め「ありがとうございました」で終える。聞き手全体に向けて説明する | `examples/zemi/notes.md` |
| **AI講義モード** | 講師のAI → 学習者のユーザー | 聞き手を「あなた」と呼ぶ。問いかけ（「どちらだと思いますか」）、ユーザーの専門への橋渡し、確認問題は「あなたならどう答えますか」、ユーザー自身の過去の答えは「あなたは〜と答えました」 | `examples/course/_work/AI活用講座_01/notes.md` |

- モードは**作るときの指示に従う**（依頼文、資料フォルダのメモ、前の回の outline.md の冒頭の順に優先）。決めたモードは outline.md の `## オプション` に書いておく
- 指示がどこにもなければ、作り始めるときにユーザーへ「原稿は発表モード（あなたが発表者）で作ります。AI講義モードにしたい場合は言ってください」と一言伝えて、発表モードで進める
- 発表モードでも、聞き手の知らない手法は、聞き手のプロフィール（専門・研究テーマ）の言葉に置き換えて一言で橋渡ししてよい（資料外なら ※ 行に根拠）

どちらのモードでも共通：
- です・ます調の話し言葉。**1枚の量**：講座は本文の枚で 400字前後（250字を切らない）、発表は 発表時間×300字÷本文の枚数 が目安（その半分を切らない）。1段落2〜4文で、段落の間は空行。1文は短く（長い文は2文に分ける）
- 1文目で前のスライドからつなぐ（「では、〜は何でしょうか」「気持ち悪さの二つ目は〜」）。最後の文で次へ渡すか結論を言う。「次のスライドです。」のような中身の無いつなぎだけの文にしない
- スライドを指して話す（「右の図で」「赤字のところ」「表の最後の行は」）。スライドの文字を棒読みしない
- 記号は言葉にする：「⇒」は「なので」、「＝」は「つまり」、式は読み方で（「De は τ 割る観測時間」「log τ が 1/T の一次関数」）
- 読まない補足は「※」で始まる行に分ける：`※（資料外の補足）…`・`※（要確認）…`・`※（図について）…`・`※解答は13枚目。`（原稿HTMLでは灰色（要確認は橙）の囲み）
- outline.md の `## 引っかかりへの手当て` で「原稿」に回したものは、そのスライドの原稿で必ず話す（書いておいた「…」の言い回しで）
- 原稿を書くときも、新しい穴を作らない：その枚の結論の「なぜ・どうやって」を言う（次の枚で言うなら「理由は次で」）、知らない側の名前の付いた法則・用語は初出で一言の意味を言う。レビューの「深」の行は、講座なら ※ の1〜2文に入れてよい

## 7. 渡す

- **スキルの部品は書き換えない・代わりを作らない**：`<skill>/` の中（scripts・assets・references・SKILL.md）は読むだけにする。作業フォルダに置くスクリプトは `build.py` と `figs.py` だけ（原稿HTMLは notes_html.py、図は figkit、一覧画像は grid.py）。部品が動かない・足りないときは、自分で直したり別のスクリプトで代えたりせず、止めてユーザーに伝える
- **渡す前に必ず確認を走らせる**：`python <skill>/scripts/check_done.py "<資料名>_スライド.pptx"`（作業フォルダを自動で見つけられないときは `--work <work>`）。**✘ が1つでも残っていたら渡さない**（直して、もう一度走らせる）
- **「できた」と言うのは、check_done が「渡してよい」を出してから**。（「止まらずに進める」の理由で）途中で区切るときは「途中です」と書き、残りの手順（描画の検査・レビュー・原稿HTML など）を並べる。スライドだけ・原稿だけで完了と報告しない
- **レビューは必ず【別のエージェント】にさせる**：自分で見て review.md を書くと、渡す前の確認が会話の記録から見つけて ✘ になる。記録が読めない道具では △ と出るので、そのときはレビューの担当とモデルを review.md の冒頭に書く
- 出力は、一覧の「出力先」があればそこ、無ければ発表フォルダ `<資料名>/` に `<資料名>_スライド.pptx`・`<資料名>_原稿.html`（例: `教科書_3.2/教科書_3.2_スライド.pptx`）。PDF は作らない。
  ビルドスクリプト・図・描画結果は `_work/<資料名>/` に残す（後で修正・再生成できるように）。
  ただし `src/`（ページ画像、数十MB）は PDF から再生成できるので、完成後に削除して同期フォルダの容量を食わないようにする
- 何枚構成か、自作した模式図はどれか（教科書にない図）、要確認の点（読み取りが怪しい数値など）を短く伝える

## 8. 原稿へのコメント（疑問点）に答える — 質問回答デッキ

「コメントした」「質問に答えて」と言われたら、**`references/answer-deck.md` を読んでから**進める（元のデッキには足さず、別の質問回答デッキを作る）。

## 続きもの（同じシリーズの次の回・次の節）を作るとき

発表の続きものは **`references/series.md`** を読む（前の回の作業フォルダを雛形にし、レビュー担当を続投させる）。講座の次の回は `references/course.md` の手順4・6。

## 講座の回を作るとき（`references/course.md` の設計メモから）

講座（`references/course.md`）で書いた設計メモ（`_work/<講座名>_0N/memo.md`）から作るときは、設計メモを講義録の代わりにする。
- 手順1の「資料を読む」は設計メモと講座の `00_README.md`（全体の地図・決め事・つまずき一覧）を読む
- **手順2は省く**：設計メモの2節が構成案の列（●見出し・青帯・図・本文の要点・ノートへ）で書いてあり、レビューも済んでいる。
  outline.md は作らず、build.py は設計メモの2節から1行ずつ書く。ユーザーへの構成案の確認もしない（地図で確認済み）。
  設計メモの8節に「レビュー後の最終版」の注記があれば、そちらに従う
- **雛形**：AI講義モードの build.py（確認問題・解答の本文を置く `qa`、notes.md を発表者ノートに入れるループ、`OUT` を講座フォルダへ）。
  第1回は `examples/course/_work/AI活用講座_01/build.py` を、2回目からは前の回の build.py をコピーして中身を差し替える
- **学習者の手元の資料の図**（自分の論文・発表の図）を載せるとき：テキスト層のある PDF なので `pdf_pages.py extract` で全頁を画像にせず、
  その頁だけを PyMuPDF で 220 dpi 程度に画像化して `_work/<講座名>_0N/src/` に置き、`pdf_pages.py crop`（カラー図は `--no-clean`）で切り出す。
  キャプションは `s.caption(b, "（資料 図3-1）")`。誤植や崩れがあってもそのまま使い、注釈は付けない
- 原稿は AI講義モード。「実際のやり取り」のスライドは作らない（ユーザーとのやり取りは質問回答デッキで返す）
- 設計メモの「事実と出典」表の出典は、原稿の ※（出典）行に残す（手元の資料は頁・式番号まで）。「未確認」の値は載せないか ※（要確認）行に出す
- 問題・解答スライドの文字量の WARN は許容する（模範解答の要素を削らない）。解答は `qa(..., size=18)` で収まることが多い
- 手順8で回答し終えたら、講座の README の「つまずき一覧」に、取り違えたこと・抜けていたことを1行ずつ足す（次の回の設計メモが読む）
