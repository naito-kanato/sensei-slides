# 完成後のレビュー（サブエージェント）

描画チェック（手順5）が ERROR 0・「←」なしになり、自分の目視も終わったあとに、**別のサブエージェントに完成したスライド画像を見せて
レビューさせる**。構成案レビュー（outline-review.md）が「何を載せるか」を見るのに対し、こちらは「できあがった1枚1枚が、
聞き手にどう見えるか」を見る。作った本人は自分の文章と図に慣れてしまい、文章調・詰め込み・図のラベルの重なりを見落とす
（過去の質問回答デッキ：機械チェックは通っていたが「簡潔でない」「図と文字がかぶる」「スペースが近い」と指摘されたでこの手順を追加）。

## 流れ

1. 手順5が終わり、`render/slide-NN.png` と `check_layout.py` の一覧がそろっていること
2. 【別のエージェント】でレビュー担当を起動する（**【上位モデル】**。構成案レビューと違い画像を見るので【標準モデル】にしない。
   ユーザーが節約を望むなら【標準モデル】でもよいが、その場合は本文の文体の指摘だけを頼む）。プロンプトは下の雛形
3. 返ってきた指摘を、メイン側が**採否と担当に分ける**。文言をそのまま写さず、基準（赤字は 1〜3か所、など）に照らして判断する
   - **内容の正確さに関わる指摘**（事実の誤り、言い過ぎ、本文どうしの矛盾）で、メイン側も納得したものは、**指摘した【上位モデル】本人に直させる**。
     同じ担当に 【続けて頼む】で「次の指摘を採用する。build.py（と notes.md）を直して、直した行を報告して」と頼む（このときだけ編集を許す）。
     直しが notes.md・answers.md と食い違わないよう、メイン側が該当ファイルのパスを渡す
   - **文体・余白・赤字・用語のそろえなど**は、メイン側（【標準モデル】でもよい）が直す。【上位モデル】の指摘文言は参考にするが、基準で判断し直す
   - 納得しない指摘は直さず、ユーザーへの報告に理由を添える
   直したら手順5（描画チェック）をやり直す
4. 2回目のレビューは、大きく直したときだけ（同じ担当に 【続けて頼む】で「直したので再確認」）。それ以外は自分の目視で終える
5. ユーザーに渡すとき、レビューの判定と直した点を1〜2行で添える

## 雛形（起動時のプロンプト）

```
あなたは、できあがったスライドの「見え方」をレビューする担当です。ファイルは読むだけで、編集・作成はしないでください（あとで私が頼んだときだけ、指定した指摘の分を直す）。

- スライド画像: <work>/render/grid-1.jpg 〜 grid-N.jpg（6枚ずつの一覧。【画像を見る】で全部見る。細かい所を確かめたい枚だけ <work>/render/slide-NN.png を開く）
- 描画チェックの一覧: <check_layout.py の出力の「スライドごとの一覧」をそのまま貼る>
- 書式の基準: <skill>/references/style-guide.md の 2節・3節（文の形・文字量）、<skill>/references/figures.md の 2節「文字」と 5節
- このデッキの種類: <ゼミ発表（発表モード）／講座（AI講義モード）／質問回答デッキ>。聞き手: <例: 本人の復習用>

1枚ずつ、次の観点で見てください。
1. 文体: 本文が体言止めの短い句になっているか。「〜できない」「〜でいられる」「〜です」のような文章になっている行を全部挙げる
2. 量: 1枚の本文が一目で読み切れる量か（目安 100〜150字。問題・解答・添削のスライドは除く）。
   削るならどの行をノートに回すか、具体的に。**少なすぎもチェックする**：中身の無い字数合わせの行（見出しや青帯の言い換え、
   「〜の見方」「別々の要因」「概念を表す模式図」のような、聞き手が何も新しく知らない句）を全部挙げ、代わりに足す数値・具体例・よくある間違いを指定する
3. 本文と図・表の間: 本文の右端と図・表の左端、本文の下端とその下の表の間に、十分な余白があるか（目安 0.4 in）。
   図を右へずらすのではなく本文を短くする前提で、どの行を短くするか
4. 図: ラベルの文字が線・曲線・点・ほかのラベルに重なっていないか（文字列を1つずつ目で追う）。ラベルが説明文になっていないか。
   図の文字が本文より一回り小さい程度（14pt 前後）に見えるか。「（概略）」などの注記が図や本文に重なっていないか。
   **図の中にしか無い前提**（軸の意味・単位・凡例の色や記号）が、本文か原稿で一度は言われているか（図を見ないと読めない結論になっていないか）
5. 1枚1メッセージ: 青帯の一文が結論になっているか。赤字の数が 1〜3か所に収まっているか。**多すぎも少なすぎもチェックする**
   （強調したい結論の言葉・対比の言葉〔透明／色／黒 のように並べて区別を見せる語〕が灰色のままになっていないか。表だけのスライドで赤が 0か所になっていないか）。
   赤を減らすときは「どの語を残すか」まで指定する（一律に 2か所にしない）
6. 表: 列の見出しがその列の真上にあるか（1列ずれて、見出しの無い列・中身の無い見出しが出ていないか）。セルの文が長すぎないか、1文字だけ次行に落ちていないか、見出しと本文の役割が分かるか
7. 全体: タイトル・●見出し・青帯の位置が全スライドでそろっているか。同じ内容が2枚に出ていないか
8. 正確さ（資料があるとき。論文紹介では必ず）: 本文・青帯・表・原稿が資料の記述と食い違っていないか、言い過ぎていないか。
   特に、数値の帰属（何の・どの検出器の・処理の前か後か）、手順の順序（同時か前後か）、赤字の結論がその図から言えることか
   （先行研究の推論が混ざっていないか）、別々の量を1つにまとめていないか（style-guide 5節「正確さの落とし穴」）。
   資料に書いていない仕組み・手順を、図や流れ図で補って資料の内容のように描いていないか（補ったなら図に「（概略）」、原稿に ※（資料外の補足）。確かでないものは載せない）。
   資料: <資料のテキスト・ページ画像のパス>、ビルドスクリプト: <work>/build.py、原稿: <work>/notes.md
9. 原稿（<work>/notes.md の ## 番号 が、その番号のスライドの原稿）: スライドと対応しているか（図があれば、どこを見て何が読めるかを言っているか。
   スライドに無いことを、スライドに書いてあるように言っていないか）。話し言葉として読み上げやすいか（1文が長すぎない、漢語や記号の読みが続かない、
   「〜である」の書き言葉になっていない）。次のスライドへのつなぎが、次で何を見るかを言っているか（「では次に」だけで済ませていない）。
   講座なら AI講義モードの口調か（「あなた」への呼びかけ・問いかけ、学習者の専門の言葉への置き換え）。
   手当てを原稿に回した枚（構成案・設計メモの「引っかかりへの手当て」）で、その説明が聞き手に伝わる言い方になっているか

出力（日本語で簡潔に。この形式で）
- 判定: 「このまま渡してよい」または「直してから渡す」
- 総評: 3行以内
- 必ず直す点: 番号つきで「[スライド番号] 何が／どう見えるか → 具体的な直し方（行の文言まで）」
- 直すとよい点: 同じ形式
良い点の列挙は不要。指摘がない観点は書かなくてよい。
```

実績：過去の論文紹介では、観点8で論文との食い違いを4か所、観点1で check_layout が拾えなかった
動詞止めの行を8行見つけた。機械の検査と作った本人の目視が通っても、このレビューは省かない。

## 判断のしかた（メイン側）

- 文体・重なり・余白の指摘は、基本はそのまま直す（反論の余地がほとんどない）。ただし**赤字の指摘は例外**：
  「2か所だけにする」のように語まで指定されても写さず、基準（1〜3か所、対比の語は揃える）で残す語を判断する
  （過去の質問回答デッキで、指摘を写して「色」「黒」まで灰色に戻し、赤が足りなくなった）
- 「量」の指摘で削る行は、ノート（notes.md）に移してから消す。問題・解答・添削スライドの要素は削らない
- 図を縮めたり左に寄せたりして逃げない。本文を短くする
- 指摘が多い（本文スライドの半分以上）ときは、1枚ずつ直すより build.py の本文を書き直すほうが早い
