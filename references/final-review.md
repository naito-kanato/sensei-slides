# 完成後のレビュー（サブエージェント）

描画チェック（手順5）が ERROR 0・「←」なしになり、自分の目視も終わったあとに、**別のサブエージェントに完成したスライド画像を見せて
レビューさせる**。構成案レビュー（outline-review.md）が「何を載せるか」を見るのに対し、こちらは「できあがった1枚1枚が、
聞き手にどう見えるか」を見る。作った本人は自分の文章と図に慣れてしまい、文章調・詰め込み・図のラベルの重なりを見落とす
（過去の質問回答デッキ：機械チェックは通っていたが「簡潔でない」「図と文字がかぶる」「スペースが近い」と指摘されたでこの手順を追加）。

## 流れ

1. 手順5が終わり、`render/slide-NN.png` と `check_layout.py` の一覧がそろっていること。仕上げ役が図の案・本文の形を変えた枚は `<work>/plan_changes.md`（枚｜前の案｜新しい案｜理由）にあるので、レビュー担当は変えた理由が妥当か（伝えたいことが弱くなっていないか）も見る
2. 【別のエージェント】でレビュー担当を起動する（モデルは指定しない。下の「指摘の型」を必ず読ませる：型の一覧があると、モデルによる見落としの差が小さくなる）。プロンプトは下の雛形
3. レビュー担当は結果を review.md に書く。作った側（【別のエージェント】が使える道具では、新しく起動した仕上げの直しの担当。SKILL.md「手順と担当」）が review.md を読み、指摘を**採否と担当に分ける**。文言をそのまま写さず、基準（赤字は 1〜3か所、など）に照らして判断する
   - **内容の正確さに関わる指摘**（事実の誤り、言い過ぎ、本文どうしの矛盾）で、作った側も納得したものは、修正案（直す文言と資料の頁）のとおりに直す。修正案だけでは直せないもの（資料を読み直さないと直せないもの）は、メインが**指摘したレビュー担当本人に直させる**。
     同じ担当に 【続けて頼む】で「次の指摘を採用する。build.py（と notes.md）を直して、直した行を報告して」と頼む（このときだけ編集を許す）。
     直しが notes.md・answers.md と食い違わないよう、該当ファイルのパスを渡す
   - **文体・余白・赤字・用語のそろえなど**は、作った側が直す。指摘の文言は参考にするが、基準で判断し直す
   - 納得しない指摘は直さず、ユーザーへの報告に理由を添える
   直したら手順5（描画チェック）をやり直す
4. 2回目のレビューは、大きく直したときだけ（同じ担当に 【続けて頼む】で「直したので再確認」）。それ以外は自分の目視で終える
5. ユーザーに渡すとき、レビューの判定と直した点を1〜2行で添える

## 雛形（起動時のプロンプト）

```
あなたは、できあがったスライドの「見え方」をレビューする担当です。ファイルは読むだけにし、結果だけを <work>/review.md に書いてください（あとで頼んだときだけ、指定した指摘の分を直す）。

- スライド画像: <work>/render/grid-1.jpg 〜 grid-N.jpg（6枚ずつの一覧。【画像を見る】で全部見る。細かい所を確かめたい枚だけ <work>/render/slide-NN.png を開く）
- 描画チェックの一覧: <check_layout.py の出力の「スライドごとの一覧」をそのまま貼る>
- 書式の基準: <skill>/references/style-guide.md の 2節・3節（文の形・文字量）、<skill>/references/figures.md の 2節「文字」と 5節
- このデッキの種類: <ゼミ発表（発表モード）／講座（AI講義モード）／質問回答デッキ>。聞き手: <例: 本人の復習用>

まず <skill>/references/final-review.md の「指摘の型」の節を読む（`python <skill>/scripts/guide.py final-review 指摘の型`）。
1枚ずつ、次の観点で見てください。型（A1〜F1）を1つずつ全部の枚に当て、指摘には型の番号を付ける。
1. 文体: 本文が体言止めの短い句になっているか。「〜できない」「〜でいられる」「〜です」のような文章になっている行を全部挙げる
2. 量: 1枚の本文が一目で読み切れる量か（目安 100〜150字。問題・解答・添削のスライドは除く）。
   削るならどの行をノートに回すか、具体的に。**少なすぎもチェックする**：中身の無い字数合わせの行（見出しや青帯の言い換え、
   「〜の見方」「別々の要因」「概念を表す模式図」のような、聞き手が何も新しく知らない句）を全部挙げ、代わりに足す数値・具体例・よくある間違いを指定する
3. 本文と図・表の間: 本文の右端と図・表の左端、本文の下端とその下の表の間に、十分な余白があるか（目安 0.4 in）。
   図を右へずらすのではなく本文を短くする前提で、どの行を短くするか
4. 図: ラベルの文字が線・曲線・点・ほかのラベルに重なっていないか（文字列を1つずつ目で追う）。ラベルが説明文になっていないか。
   図の文字が本文より一回り小さい程度（14pt 前後）に見えるか。「（概略）」などの注記が図や本文に重なっていないか。
   **図の中にしか無い前提**（軸の意味・単位・凡例の色や記号）が、本文か原稿で一度は言われているか（図を見ないと読めない結論になっていないか）
5. 1枚1メッセージ: 青帯の一文が結論になっているか。赤字の数が 1〜3か所に収まっているか。**多すぎも少なすぎもチェックする**
   （強調したい結論の言葉・対比の言葉〔透明／色／黒 のように並べて区別を見せる語〕が灰色のままになっていないか。表だけのスライドで赤が 0か所になっていないか）。
   赤を減らすときは「どの語を残すか」まで指定する（一律に 2か所にしない）
6. 表: 列の見出しがその列の真上にあるか（1列ずれて、見出しの無い列・中身の無い見出しが出ていないか）。セルの文が長すぎないか、1文字だけ次行に落ちていないか、見出しと本文の役割が分かるか
7. 全体: タイトル・●見出し・青帯の位置が全スライドでそろっているか。同じ内容が2枚に出ていないか
8. 正確さ（資料があるとき。論文紹介では必ず）: 本文・青帯・表・原稿が資料の記述と食い違っていないか、言い過ぎていないか。
   特に、数値の帰属（何の・どの検出器の・処理の前か後か）、手順の順序（同時か前後か）、赤字の結論がその図から言えることか
   （先行研究の推論が混ざっていないか）、別々の量を1つにまとめていないか（style-guide 5節「正確さの落とし穴」）。
   資料に書いていない仕組み・手順を、図や流れ図で補って資料の内容のように描いていないか（補ったなら図に「（概略）」、原稿に ※（資料外の補足）。確かでないものは載せない）。
   資料: <資料のテキスト・ページ画像のパス>、ビルドスクリプト: <work>/build.py、原稿: <work>/notes.md
9. 原稿（<work>/notes.md の ## 番号 が、その番号のスライドの原稿）: スライドと対応しているか（図があれば、どこを見て何が読めるかを言っているか。
   スライドに無いことを、スライドに書いてあるように言っていないか）。話し言葉として読み上げやすいか（1文が長すぎない、漢語や記号の読みが続かない、
   「〜である」の書き言葉になっていない）。次のスライドへのつなぎが、次で何を見るかを言っているか（「では次に」だけで済ませていない）。
   講座なら AI講義モードの口調か（「あなた」への呼びかけ・問いかけ、学習者の専門の言葉への置き換え）。
   手当てを原稿に回した枚（構成案・設計メモの「引っかかりへの手当て」）で、その説明が聞き手に伝わる言い方になっているか

結果は <work>/review.md に次の形で書き、返答には判定と「必ず直す点 N件・直すとよい点 N件」の1行だけを書く。必ず直す点には、直す文言と根拠（資料の頁）まで書く（作った側がそのまま直せるように）。
出力（日本語で簡潔に。この形式で）
- 判定: 「このまま渡してよい」または「直してから渡す」
- 総評: 3行以内
- 必ず直す点: 番号つきで「[スライド番号] 何が／どう見えるか → 具体的な直し方（行の文言まで）」
- 直すとよい点: 同じ形式
良い点の列挙は不要。指摘がない観点は書かなくてよい。
```

実績：過去の論文紹介では、観点8で論文との食い違いを4か所、観点1で check_layout が拾えなかった
動詞止めの行を8行見つけた。機械の検査と作った本人の目視が通っても、このレビューは省かない。

## 指摘の型（レビュー担当は、型を1つずつ全部の枚に当てる）

観点（雛形の1〜9）を「どこを疑うか」まで細かくしたもの。型ごとに、**確かめ方**のとおりに資料・構成案・原稿と突き合わせる。
読んだ印象で探すのではなく、型の順に当てていくと、モデルによる見落としの差が小さくなる。例は過去のレビューで実際に出たもの。

### A. 資料との食い違い（正確さ）

| 型 | 確かめ方 | 例 |
|---|---|---|
| A1 数値の写し違い | 本文・図・原稿の数値を1つずつ、資料の該当の文と並べる。**不等号（以上・未満・≳）・「約」・桁・単位**まで同じか | 「≳70 M⊙」が「約70 M⊙」に、「≳210 km」が「≈210 km」に |
| A2 数値の帰属 | その数値が**何の・どこの・いつの**量か（どの装置・どの系・処理の前か後か・どの条件か）を資料で確かめる | 700 W は「装置に入る光」ではなく「ビームスプリッタに入る光」 |
| A3 理由の取り違え | 「AだからB」と書いた所は、資料が挙げる理由と同じか（別のもっともらしい理由にすり替わっていないか） | 資料は「質量が足りない」と言うのに「75 Hz まで近づけない」と書く |
| A4 言い過ぎ | 必要条件を十分条件に、推定を確定に、「示した」を「証明した」に、限られた条件の結果を一般に、していないか。設計メモ3節（裏取り）の行の限定（または・一部・〜とされる・考慮・望ましい など）を外していないか | 「10 ms より短いので同じ信号だとわかる」（時間差は必要条件にすぎない） |
| A5 出どころの印 | 資料に無いことに「※（資料外の補足）」が付いているか。原稿で「講師（発表者）の解釈」と断った所は、スライドの該当の行にも「（講師の解釈）」があるか。**逆に**、資料にあることを資料外と断っていないか | 論文に無い「軌道の縮む速さが放出エネルギーと合う」が印なし／要旨にある値を資料外扱い |
| A6 締め・言い換えのずれ | 締めの一文・青帯・赤字が、元の結論を言い換えたときに意味が変わっていないか | 「20万年に1回未満の偶然で、2台がとらえた」（偶然の頻度と信号の頻度の取り違え） |
| A7 古い情報 | 時とともに変わる値（制度・基準の版、統計、法令・指針、料金、数）は、今年の改定・新版を1回検索して、使った版が最新か確かめる。出典に版か年が無ければ指摘する | 新しい版（Ver.3.0）が出ているのに、前の版の領域の数と項目で説明 |

### B. 図

| 型 | 確かめ方 | 例 |
|---|---|---|
| B1 図にしか無い前提 | 軸の量と単位・凡例の色や記号・図の中の略語が、本文か原稿で一度は言われているか | 紫の線が何かを言わずに「紫線」と読ませる |
| B2 図と文の食い違い | 本文・注記・原稿が指すもの（色・印・名前・数値）が、図に本当にあるか | 図に無い「赤い輪」を原稿が見るよう促す |
| B3 図の見え方 | 図だけを見て：小さすぎて読めない・回転や反転・切れ・ラベルの重なり・赤の使いすぎ・説明文のラベル | 図が180°回転して凡例が逆さ／目盛りが 6pt |
| B4 図にできる文字 | 図が文字の箱（と矢印）だけの枚、数値を2つ以上比べる・割合・時間の変化・順位を文字だけで書いた枚を挙げ、棒グラフ・折れ線・表・模式図にできないかを書く（数値は設計メモの事実の表から） | 研究の数値を文字の箱に並べただけ → 棒グラフにすれば差がひと目で分かる |

### C. 本文

| 型 | 確かめ方 | 例 |
|---|---|---|
| C1 文体 | 1行ずつ、文章調・動詞止め・行末に残った「・」が無いか | 「信号の周波数が時間とともに上がる」 |
| C2 量と重複 | 1枚 100〜150字か、中身の無い行（青帯の言い換え）が無いか、同じ内容が2枚に出ていないか | 「連星パルサーで間接的に確認」が2枚の本文に |
| C3 強調と青帯 | 赤字が根拠の要の語・数値か、決め手の短い一文（全角20字まで・1か所。場合分け・2つ並べた・展開（前 → 後）の枚は、塊ごとに1文で2か所まで）か（1〜3か所。20字を超える・その外で2文以上は多い）。青字が強調に使われていないか（図の色との対応・対になる側だけ）、青帯が結論か（図の種類の説明になっていないか） | 青帯「時間と周波数の図で、…」は前半が図の説明 |

### D. 構成案との突き合わせ

| 型 | 確かめ方 | 例 |
|---|---|---|
| D1 手当ての抜け | 構成案の「引っかかりへの手当て」を1行ずつ、言われた所（本文・原稿）に入っているか | 「SN 比（信号と雑音の比）を初出の本文に」が無い |
| D2 筋 | 筋の問いの枚で問いを立てているか、答えの枚で答えているか、原稿の1文目が「前の枚から」の語どおりか | 3枚目で問いを立てないまま、14枚目で「最初の問い」と言う |
| D3 要点の抜け | 構成案の本文の要点が、本文か原稿のどちらかに全部あるか | 「背景は多めの見積り ⇒ 評価は控えめ」が抜け |
| D4 縮めて開いた穴 | 構成案（設計メモ）の本文の要点にあった「何の数か」「名前の付いた語の中身の一言」「予告の一言」が、字数を縮めたときに本文からも原稿からも消えていないか（推論距離の穴が開き直す。inference-distance.md 2節） | 要点の「件数 A・B」が本文で「多い：A と B」になり、何の数か分からない |

### E. 原稿

| 型 | 確かめ方 | 例 |
|---|---|---|
| E1 作業の残り | TODO・「ノートへ：」・骨組みの文・コメント記号が、読み上げる文に残っていないか | 原稿に「ノートへ：真空は…」 |
| E2 読み上げにくさとつなぎ | 1文が長すぎないか、記号や漢語が続かないか、1文目と最後の文に中身があるか、つなぎが二重になっていないか | 「次の枚で扱います」→「次の枚では」と二度 |
| E3 聞き手に合わない説明 | 聞き手が知っている前提を長々と説明していないか、知らない語を説明なしに使っていないか | 物理の聞き手に「Hz は1秒あたりの回数」 |

### F. 全体

| 型 | 確かめ方 | 例 |
|---|---|---|
| F1 そろい | 一覧の画像で、タイトル・本文の書き始め・図の位置と大きさがそろっているか | 本文の書き始めが 2・7・11枚目だけ低い |
| F2 書き手のぶれ | 前半と後半（制作役が2人の回）で、語尾・用語の表記・赤字の量・本文の形の使い方・原稿の長さと話し方がそろっているか | 前半は体言止め・後半は「〜である」、前半は赤字1か所・後半は3か所、後半だけ原稿が半分の長さ |

## 判断のしかた（メイン側）

- 文体・重なり・余白の指摘は、基本はそのまま直す（反論の余地がほとんどない）。ただし**赤字の指摘は例外**：
  「2か所だけにする」のように語まで指定されても写さず、基準（1〜3か所、対比の語は揃える）で残す語を判断する
  （過去の質問回答デッキで、指摘を写して「色」「黒」まで灰色に戻し、赤が足りなくなった）
- 「量」の指摘で削る行は、ノート（notes.md）に移してから消す。問題・解答・添削スライドの要素は削らない
- 図を縮めたり左に寄せたりして逃げない。本文を短くする
- 指摘が多い（本文スライドの半分以上）ときは、1枚ずつ直すより build.py の本文を書き直すほうが早い
