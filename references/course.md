# 講座を作る（テーマか資料 → 全体の地図 → 各回の設計メモ → スライド）

SKILL.md の冒頭「まず決める：発表か講座か」で**講座**になったら、この手順で進める。
講座は、講師のAIが学習者（「あなた」）に教える**連続講座**（全N回）。1回ずつ作り、前の回のコメントと答えを次の回に反映する。

ここで受け持つのは「何をどの順に、どこまで正確に教えるか」を決めるところ（手順1〜4）。スライド・原稿・原稿HTML・コメントへの回答は
SKILL.md の手順3〜8（図 → ビルド → 描画確認 → 完成後レビュー → 原稿HTML → 質問回答デッキ）で作る（この手順書の手順5・6）。

もとになった実例：AI とのチャット講義の講義録から、全回のデッキを作った講座。
その講義録にあたるものを、講座では自分で作る。ただし**ユーザーが読むのはスライドと原稿HTMLだけ**で、
講義録のような読み物は作らない（同じ中身を2回読ませない）。代わりに作業用の**設計メモ**を残す。
作者はこの手順で、データ解析（全5回、学習者の論文を橋渡しに使用）・電子工学・SNS 運営などの講座を作った。
それらの作業フォルダはこのリポジトリに含まれない。講座の見本は `examples/course/`（`AI活用講座/00_README.md`＝講座の README、`_work/AI活用講座_01/` の `memo.md`・`build.py`・`notes.md`＝第1回の設計メモ・ビルドの雛形・AI講義モードの原稿）。迷ったらこれを雛形にする。

| 作るもの | 置き場所 | 読む人 |
|---|---|---|
| 講座フォルダと README（講座ID・保存先・全体の地図・決め事・つまずき一覧） | `<講座フォルダ>/00_README.md` | ユーザーも見てよい |
| 各回の設計メモ（要点・事実と出典・問題・図の案） | `_work/<講座名>_0N/memo.md` | AI（作業用） |
| スライド・原稿HTML・質問回答デッキ | `<講座フォルダ>/0N_<題>_スライド.pptx`・`_原稿.html` | ユーザー |

雛形は `assets/course/README.md`（講座の README）と `assets/course/memo.md`（設計メモ）。

**モデル**：全部メインのセッションのモデルで進め、【別のエージェント】にモデルを指定しない（SKILL.md「必ず守る」）。
事実の裏取りの質は、設計メモの「事実と出典」の表と、レビュー担当に渡す観点（outline-review.md の監査・final-review.md の指摘の型）で保つ。

## 資料の扱い：土台か、橋渡しか

講座は資料がなくても作れる（テーマだけ → 調べて裏を取る）。資料があるときは、どちらの使い方かを手順1で決める。

| 使い方 | 例 | 中身の出どころ | 事実の表の出典 |
|---|---|---|---|
| **土台**（資料で講座を作る） | 「この教科書で全5回の講座を」「この論文を3回で理解したい」 | 資料。地図は資料の章立てを元に、学習者に合わせて並べ直す | 資料の頁・式・図番号。資料外の補足だけ Web で裏を取り、※（資料外の補足）に出す |
| **橋渡し**（テーマの講座に手元の資料をつなぐ） | 「統計の手法を一から。自分の論文を参考に」 | 一般の文献（Web で裏を取る） | 書名・URL。資料からは「卒論の式(2-4)は…」の対応だけ引く |

- 土台のときは、資料を SKILL.md の手順1（`pdf_pages.py extract`）で全部読んでから地図を作る。資料に書いていないことを資料の主張にしない
- 1回の発表で終わるなら講座にしない（SKILL.md の発表の手順）。講座にするのは、回を分けたい・確認問題で確かめたい・前の回のつまずきを次に活かしたいとき

## 手順

**誰がどの手順をするか**（【別のエージェント】が使える道具。SKILL.md「手順と担当」）：手順1（ヒアリング）と、ユーザーへの確認（地図を見せる）はメイン。手順2・3は地図の担当、手順4は設計の担当（骨）・裏取りの担当2人・直しの担当、手順5は制作役（図と本文・原稿）と仕上げ役（組んで直す・原稿HTML）。担当の起動とレビュー担当への依頼はメインがする。下の「メイン」は、【別のエージェント】が無いときは自分のこと。

### 1. ヒアリング（短く）

聞くのは次の8つだけ。**テーマと詳しさは必須**（分からなければ聞くまで進まない）。聞く順は、必須 → 資料があればもらう（既定はなし）→ 学習者のプロフィールを勧める（任意）。ほかは、メモリや会話から分かるものは聞かずに使い、分からないものは既定値で進めて一言伝える。
【質問】はボタンで**1回・3問・各3択**にまとめる（どの道具でも出せる大きさ。「その他」の自由記入は道具が付ける）。テーマが依頼文に無ければ、それだけ先に文で聞く。依頼文で分かる問いは省く。
- ① **詳しさ**（必須）：初学者／多少知っている／かなり知っている。問いの文に「学習者が自分でない（後輩・受講者など）ときは、その他にどんな人かを書く」と添える。
  そう答えられたら「誰が見るか」を受講者一般にし、詳しさとプロフィールはその人のものにする（下の注意）
- ② **回数**：3回／5回／おまかせ（おまかせなら下の既定で決め、地図で提案して直してもらう）
- ③ **資料**：テーマだけ／手元の PDF を土台に／あとで決める
- ゴール・1回の分量・誰が見るかは聞かずに既定値（下の表）。学習者のプロフィールは、答えのあとに一言で勧める（任意）
- 答えが出たら、地図を作り始める前のメッセージに、設定の一覧（`slide_profile.py --table --kind 講座 --set …`）と、ゴール・回数・1回の分量・誰が見るかを貼り、
  「この設定で進めます。変えたい所があれば、いつでも言ってください」と一言添えて、**返事を待たずに**地図へ進む（地図はいつもどおりユーザーに見せて OK をもらう）

| 項目 | 既定値 |
|---|---|
| テーマと範囲（どこまで） | — （これだけは必須。資料が土台なら「資料のどこまで」） |
| 資料（任意） | なし。あれば「土台」か「橋渡し」か（上の表）。フォルダに入れたと言われたら `materials.py <講座フォルダ> --collect --source` で講座フォルダの `資料/` に格納する（steps.md「資料の受け取り」） |
| **テーマへの詳しさ** | — （必須。初学者／多少知っている／かなり知っている。丁寧さがこれで決まる：初学者 0・多少知っている 1・かなり知っている 2） |
| 学習者のプロフィール（専門・研究テーマ・よく知っていること） | 任意。必須を聞いたあとに「書いてもらえると、言い換えと止まる所の判定がよくなります」と勧める。メモリや会話から分かる専門があれば使ってよい |
| ゴール（何ができるようになりたいか、使い道） | 「その分野の人と話が通じ、資料が読める」。手元の資料が自分の研究なら「自分の研究で使ったものを原理から説明できる」 |
| 回数 | 5〜8回（テーマの広さで決め、地図で提案して直してもらう）。狭いテーマなら3〜4回 |
| 1回の分量 | 本文10〜15枚＋確認問題（表紙・確認問題・解答は数えない。設計メモの段階で `check_memo.py` が数える） |
| 誰が見るか | 依頼者本人だけ。後輩・同僚にも見せると言われたら「受講者一般」にする（下の注意） |

**受講者が本人だけでないとき**（以前の講座では途中で「研究室の後輩にも見せたいので、依頼者本人を前提にしないで」と指定された）：
- README の「学習者とゴール」を「受講者とゴール」にし、受講者の層（例：研究室の学生）と、前提にする知識の水準を書く。依頼者は「作成者」
- 依頼者の論文・ノートブックは「教材として引く例」にする。原稿で「あなたの卒論」「あなたが書いた」と言わず、「〇〇さんの卒論（2025）」
  「研究室のノートブック」と呼ぶ。「〇〇をやってきたあなたなら」のような依頼者の経歴に頼った言い回しも、「〇〇を習った人なら」に変える
- 途中で切り替えたら、作った回の原稿も直す（`grep -n "あなたの\|あなたが\|やってきた" notes.md` で拾える）。確認問題の「あなたの卒論では」も直す

**手元の資料**（学習者の卒論・発表・講義資料など）を橋渡しに使うとき（以前の講座ではユーザーがテーマと一緒に指定した）：
- 講座の**中身の出どころではなく、橋渡しの材料**として使う（「卒論の式(2-4)は…」）。中身そのものが資料にあるなら「土台」にする
- 資料に**コード・設定ファイル・実行結果**（ノートブック、ライブラリ、config、診断出力）があるときは、仕組みはドキュメントやコメントでなく
  **コードで読み**（例：コメントに書いてある値と、実際に使われている値が違う）、説明に使う値は**実物の出力でも確かめる**。
  既定値だけで説明すると、実際に tune した後の値（以前の講座では、調整後の値が既定値と大きく違っていた）と食い違う。
  「実物を読む」スライドを1枚置くと、受講者が自分の出力を読めるようになる。レビュー担当にも実物のファイルを読ませる
- フォルダが作業ディレクトリの外にあることが多い（例：自分の論文のフォルダ）。**読むだけで、書き換えない・コピーしない**。
  PDF は PyMuPDF でテキストを抜き出して scratchpad に置き、式や図はその頁だけ画像にして見る（全頁の画像化はしない）
- フォルダが大きいときは、まず中身を一覧して、テーマに関わるもの（論文本文・予稿・講義資料）だけを読む
- 読んだものの場所を README の「参考にする手元の資料」に書く（次の回もレビュー担当もそこから読む）
- 学習者の資料の書き方が一般と違う・あいまいな所（定義のない記号、言葉の使い分け）は、**責めずに「一般にはこう書く」と並べる**。
  この方針を README の決め事に書いておく。誤植の指摘はしない

### 2. 講座フォルダと README を作る

- 講座フォルダ：作業ディレクトリ直下に `<講座名>/`、作業フォルダは `_work/<講座名>_0N/`。**両方に同じ講座名を使う**
  （例 `AI活用講座/` と `_work/AI活用講座_01/`）
- `00_README.md` を `assets/course/README.md` から作る。必ず埋める行：
  - `- 書き出しの保存先: このフォルダ（<講座フォルダ名>）`
  - `- 講座ID: XX`（英字2〜3文字。既存の講座と重ならないもの。使用中のIDは `grep -h "講座ID" */00_README.md` で見る）
  - 原稿のモード：**AI講義モード**（話し手＝講師のAI、聞き手＝「あなた」と呼ぶ学習者）
  - 学習者の背景とゴール（手順1）、資料の場所と使い方（土台／橋渡し。テンプレートの「学習者とゴール」節に足す）
- この2行（保存先・講座ID）があると、原稿HTMLのコメントの書き出しと移動がその講座で閉じる（`references/answer-deck.md`「原稿HTMLのコメント機能」）

### 3. 全体の地図（全N回）

地図はピラミッドの上の段：回ごとの題・ゴール・中身の話題・橋渡しまでにする。**数値・版・年・件数などの具体の事実は書かない**（裏が取れていない値が上の段に入ると、各回の設計がそれを確かめた事実として読む。以前の講座では、地図に書いた古い認定率が第1回の設計まで残った）。どうしても書くなら「（未確認）」を付ける。

README の「全体の地図」節に、回ごとに1〜2行で書く：題、**ねらい**、この回で言えるようになること、前提にする回、予告する回。
- **ねらい**は、`python <skill>/scripts/story.py --aims` の一覧から回ごとに1つ（なぜこの形か・仕組みが分かる・使えるようになる など）。
  ねらいごとに既定の話の型が決まっていて、設計の担当はそれを使う（筋が、強い数字や目立つ話に引っぱられないように）。ユーザーが地図で見て直せる言葉にしてある。
  ねらいの列が無い地図（前の版で作った講座）では、設計の担当がその回のねらいを選び、`story.py --aim <work> <ねらい>` で地図に列を足して書く（ユーザーに聞かなくてよい）
- 順番は「前の回の言葉だけで次の回が説明できる」ように並べる。学習者の背景から入れる橋渡し（旧分野との対応）を各回に1つ以上
- 資料が土台なら、各回に資料の範囲（章・頁）を書く。資料の順のままでなく、前の回の言葉で説明できる順に並べ直してよい
- 回どうしの伏線（「→ 第N回」）を地図の段階で決めておく。スライドの青字の伏線はここから取る
- 手元の資料があるときは、橋渡しの欄に資料の場所（「卒論の式(2-4)」「表2-1」）まで書く。地図の段階で資料に**実際にあるか**を確かめる
  （以前の講座では「表2-1で〇〇が読める」と書いたが、表2-1にその値はなかった。レビューで見つかった）
- 地図はユーザーに見せて、回数や順番を直してもらう（大きな判断なのでここだけは確認をとる）。チャットに短い表
  （回・題・中身・橋渡し先）を出し、【質問】で「このままでOK／縮める」を聞く。回数は作りながら増やしてもよい。増やしたら README の地図を直す

### 4. 各回の設計メモ（1回ずつ作る）

担当ごとに要る所だけ読む：設計の担当は 4a、レビュー担当は 4b、設計メモの確認（check_memo）の中身は 4c。

#### 4a. 流れと設計メモの中身（設計の担当・メイン）

**全回を一度に作らない。** ユーザーが前の回を読み、コメント・答えを書き出したあとで次の回を作る（前の回のつまずきを反映できる）。
ユーザーが「まとめて作って」と言ったときだけ続けて作る。

**上から書く**（`references/story.md`「考える順は上から」）。具体の事実を先に集めてから組むと、筋が集めた資料の形（沿革なら年代順）に引っぱられ、
裏取りの検索結果を抱えた会話も長くなる（以前の講座の第1回では、設計の担当が裏取り70回のあとに設計メモを一度に書き、会話が42万トークンまで伸びて使用量の約4割、
並びは年代順になって問いが5枚目の原稿にしか出なかった）。

| 順 | 誰が | やること |
|---|---|---|
| ⓪ 数字 | 数字を探す担当2人（同時に。レビュー担当の先読みも同時） | 地図のこの回の行と学習者から問いの候補を立て、それに効く**比べられる数字の組**（同じ単位・分母・時点で2〜8区分）を `<work>/data_N.md` に3組まで（`brief.py 数字を探す担当 <work> --n 1`・`--n 2`。1人目は差と意外、2人目は変化と内訳）。組ごとに「別の読み方」（驚きに見えない読み方）を1行。比べられる組が無い回（理論の導入・手順の習得など）は無理に出さず「見つからなかった：理由」を書く（正規の結果）。数字は話の裏付けではなく、筋の「しかし」を作る材料なので、設計の前に探す。強い組は、回のゴールから選んだ話の型の しかし の拍に据える（数字のための型は無い）。無い・弱いなら、データ無しの しかし（意外・疑い・限り）で組む |
| ① 骨 | 設計の担当 | **data_N.md を読んでから**、地図のこの回のゴールから、1節（ゴール・前提・**筋の4行**・**話の型**）→ 2節の**青帯の並び**（まず型の拍1つにつき1行） → 2節の**本文の形と図で見せるもの**（その枚で何をどう伝えるか）→ 2節の本文の要点と〔事実N〕→ 6節（問題）→ 3節の**事実の行**の順に書く。3節は確かめる事実を1行ずつ並べるだけで、値は知っている範囲の仮の値か空、確認は「未確認」。Web は筋を決めるのに要る数回だけ（今の版はどれか、最新の統計は何年か）。`check_memo.py` のあと `facts.py split <work> --n 2` |
| ② 裏取り | 裏取りの担当2人（同時に。レビュー担当の先読みも同時） | `<work>/facts_1.md`・`facts_2.md` の先頭のとおり。1行確かめるごとにファイルを書き直す。設計の担当が置いた値と違えば「違う：…」 |
| ③ まとめ | メイン | `facts.py merge <work>`（3節に戻し、違った行を facts_diff.md に） |
| ④ レビュー | レビュー担当（続けて） | 下の観点で memo_review.md に |
| ⑤ 直し | 直しの担当（**新しく起動**。設計の担当を続けない） | memo.md・memo_review.md・facts_diff.md を読み、違った事実に合わせて青帯と筋を直し、レビューの採否を決めて直す。`check_memo.py` → `scaffold.py <work>` まで |

②を2人にするのは、行が多い回（30行ほど）を1人で調べると、検索の結果で会話が伸び、1回ごとの操作が重くなるから。行が10行に満たなければ1人でよい（`--n 1`）。
⑤を新しい担当にするのは、①の会話を続けると、裏取り前の考えを抱えたまま直すうえ、長い会話のまま何度も読み直すから（直しに要るのは3つのファイルだけ）。
【別のエージェント】が無いときは、同じ順に自分で行い、②は facts_1.md から1行ずつ書き足す。

**書き始める前に、レビュー担当を起動して先読みさせておく**（バックグラウンド。事実と出典の確認・式の再計算を受け持つ。モデルは指定しない）。読ませるのは README、
資料のうちこの回で使う章（テキスト抽出と、式・図の頁画像）、`references/style-guide.md` の 3・5節と `references/figures.md` の 1節、
`references/outline-review.md` の「B」の観点。担当には「読み終えたら『準備完了』とだけ返して止まる」と頼む（outline-review.md「A」の形で、「構成案」を「設計メモ」に読み替える）。
メモを書いている間に読み終わるので、レビューの待ちが短くなる（以前の講座の第1回：先読み約6分、レビュー約5分）。
手元の資料をまるごと読ませると重い（約50頁の論文のテキスト全部で先読み約18万トークン）。この回に要る章に絞る。

`_work/<講座名>_0N/memo.md` を `assets/course/memo.md` の形で書く。中身：
1. **この回のゴール**（言えるようになること、3つまで）と前提（前の回の何を使うか）
2. **話の順番**：**構成案（outline.md）の列で書き、構成案を兼ねる**（# ／●見出し／青帯（結論）／図で見せるもの／
   本文の要点／ノートへ・橋渡し）。1行＝スライド1枚。表紙と問題・解答の行も入れ、表の下に「青帯だけを上から読む」を1行で書く。
   こうすると outline.md を別に作らずに済む（`assets/course/memo.md` の2節がこの列になっている）
   - **確認問題には〔ゴールN・M枚目〕、解答には〔要素：…／…〕**（6節。カードが、解答の原稿で戻る枚と、削ってはいけない要素を書き手に渡す）
   - **本文の要点の数値・例には〔事実N〕**（N は3節の表の行。カードがその行を書き手に渡す。無ければ check_memo が △）
   - **表の前に話の筋を書く**（1節の終わりの筋の表：状況・複雑化・問い・答え。複雑化と問いは「型」を先に選ぶ）。問いは学習者の疑問の形で前のほうの枚に、答えは回のゴールの1つ目に合わせて後ろのほうの枚に。
     2節の「前の枚から」に、前の枚の青帯からのつながりを「しかし（意外）」のように語と種類で書く。`references/story.md`
   - ゴールごとに、それを見せるスライドと、確かめる問題が1つずつあるようにする（以前の講座では、ゴール「自分の論文のどこに当たるか指せる」
     を確かめる場面がなく、レビューで対応表のスライドを足した）
   - 学習者の背景への橋渡しは、その回の山場（いちばん効く対応）を後半に置くと、まとめにつながる
   - **書くときから穴を避ける**（講座は丁寧さ 0。学習者が実際に止まった所はこの3つだった）：その枚の結論の「なぜ・どうやって」をその枚に書く（次の枚で説明するなら「理由は次で」と予告）／知らない側の名前の付いた法則・用語は初出で何を表すかの一言（式の形・見え方だけにしない）／あとの枚や確認問題の答えで使う前提は、使う前の枚で出す（outline-review.md「書くときから避ける」）
   - **本文（表紙・確認問題・解答を除く行）は10〜15行**。少ないときは、たいてい話が抜けている（前提の説明・具体例・数値の例・
     つまずきやすい所・前後の回とのつながり）。足すか、回をまとめる。どうしても外れるなら、表の下に「枚数の理由：…」と書く
3. **事実と出典の表**：数値・定義・式・図の向き・固有名詞を1行ずつ。「主張｜値｜出典｜確認」
   - 資料が土台なら、出典は資料の頁・式・図番号。資料外のものは Web で裏を取る
   - 確認は **Web検索（WebSearch / WebFetch）で裏を取る**。教科書・総説・公的な資料を優先し、出典（書名・URL）を残す
   - **時とともに変わる事実は、最新の版を先に探す**（制度・基準の版、統計、法令・指針、料金、組織・施設の数、製品の仕様）。
     検索語に今年の年と「最新」「改定」「新版」を入れ、公式のページで版と改定日（施行日）を確かめてから値を拾う。出典には版か年（「Ver.3.0（2025年）」「2024年10月時点」）を書く。
     見つかったのが古い版だけなら、値に「〇年時点」を付け、新しい版の有無を「未確認」に書く（以前の講座では、完成後のレビューで新しい版が見つかり、事実の表・本文・原稿を作り直した）
   - 裏取りは、**確かめた行から順にファイルへ書き足す**（途中でも読め、止めても無駄にならない。`facts.py split` が作る facts_N.md の形）
   - 出典は、ほかの人があとで同じ資料を開けるように書く（URL・DOI・「題名」・著者と年・条番号・頁や図の番号のどれか）。「厚生労働省」「薬機法」だけでは書かない。設計メモの確認（`check_memo.py`）と渡す前の確認（`check_done.py`）が、○ の行にこの手がかりがあるかを見る
   - 裏が取れないものは「未確認」とし、スライドに載せるなら原稿の ※（要確認）行に出す。確信のない数値は載せない
   - 学説が割れているもの（例：水の Tg）は「諸説あり」と書く
   - 手元の資料から引く事実（式・図・数値・書き方）も1行ずつ載せ、出典に頁・式番号を書く。**資料に書いていないことを資料の主張にしない**
     （以前の講座では、学習者の論文に定義のない量を「論文ではこう定義している」と書いてしまい、レビューで直した。正しくは「定義はなく、こう読むと一致する」）
   - 係数や規約が文献で違うもの（E の 1/2 の付け方など）は、どれに合わせるかを決め、違う書き方の出典も並べる
4. **用語・記号の決め事**（全回でそろえる）：記号、図の軸の向き、色の割り当て、呼び方。レビューのあと、スライドを作る前に README の決め事に写す
   （README と設計メモで書き方が割れると、次の回の設計メモが README のほうを読んで食い違う）
5. **図の案**：テーマか難所のどちらを見せるか（`references/figures.md` 1節の基準）
6. **確認問題と模範解答**（**6問ちょうど**。スライドは1枚に3問ずつで、確認問題2枚（N-1〜N-3・N-4〜N-6）と解答2枚。check_memo と check_layout が数える）：問題ごとに**型を選んでから**書く（〔型：…〕＝定義・仕組み・誤り指摘・当てはめ・比べる・計算。6問で3種類以上。check_memo が △）。定義を言わせる・仕組みを説明させる・誤りを指摘させる、を混ぜる。
   手元の資料があるなら1問は学習者の資料に当てはめる（「あなたの卒論のエラーバーは…」）
   - 答えが一意に決まるよう、前提（既知の量、変えない条件、記号の定義）を問題文に入れる。誤りを指摘させる問題の模範解答には反例を付ける
7. **前の回から反映すること**：前の回のコメント・答え（質問回答デッキと README の「つまずき一覧」）から、
   この回の冒頭で補うこと・言い換えること。あれば冒頭に「前回のつまずき」を1枚置く。
   前の回の設計メモの8節にある「第N回に回す点」（レビュー担当のメモ）も読む

#### 4b. 設計メモのレビューの観点（レビュー担当）

設計メモができたら、先読みさせておいた**レビュー担当**に 【続けて頼む】でレビューを頼む。観点は
`references/outline-review.md` の「B」の1〜7に加えて：
- **事実の確認**：表の値と出典が合っているか、未確認のまま断定していないか、式を自分で再計算して合うか。
  時とともに変わる値は、最新の版か（今年の改定・新版を1回は検索して確かめる）、出典に版か年があるか
- **資料の引き方**：資料に書いていないことを資料の主張にしていないか、図の読みが合っているか
- **ゴールと問題**：ゴールごとに見せるスライドと確かめる問題があるか、問題の答えが一意か、模範解答に誤りや不足がないか
- **README との食い違い**：記号・係数の書き方が README と割れていないか
- **後の回に回す点**：この回では触れないが後の回で使う指摘（設計メモの8節に残す）
- **推論距離の監査**：`references/outline-review.md` の「B」の8を、「構成案」を「設計メモ」、「outline.md 冒頭」を「設計メモの1節」に読み替えて。
  聞き手は1節の「聞き手の前提知識」の人、丁寧さは1節の値（講座の既定は 0＝入門。「要」の穴は全部架ける）。
  出力の「推論距離」は穴1つを1行で（`[番号] 「A ⇒ B」｜種類｜要否｜補う前提：…｜使う所：…｜架け方：…`）。「深」の行は手当てに入れなくてよく、原稿の ※ の候補にする
出力は「判定／総評3行／必ず直す点／直すとよい点／第2回以降に回す点／推論距離」。
**レビューの結果はそのまま `_work/<講座名>_0N/memo_review.md` に残す**。推論距離から妥当なものを選んで2節の表（本文・ノート）を直し、
9節「引っかかりへの手当て」に `- [スライド番号]` で1行ずつ書く（採らなかったものも理由つきで。選び方と架け方は outline-review.md「推論距離の扱い」）。「必ず直す点」は自分でも資料で確かめてから反映し、
反映したことを8節に書く。ユーザーへの確認は大きな判断が要るときだけ。

#### 4c. 設計メモの確認（check_memo）

**レビューに頼む前と、指摘を反映したあとに、設計メモの確認を走らせる**：`python <skill>/scripts/check_memo.py _work/<講座名>_0N/memo.md`。
本文の枚数（既定の10〜15枚）、流れ図の数、図の無いスライド、中身の具体さ、出典の書き方、前提知識と丁寧さの行、
レビューの推論距離と9節の手当ての突き合わせを見る（渡す前の確認も、memo_review.md と9節を突き合わせる）。✘ は直す。△（枚数が外れる）は、話を足すか回をまとめるか、2節に「枚数の理由：…」を書いてから進む。
スライドを作ってからでは枚数を直しにくいので、この段階で決める
- **本文の形**：2節の表に「本文の形」の列を作り、枚ごとに文字の組み方を決める（`references/structures.md`。同じ形の組は4枚まで）
- **図の無いスライドは ✘**：本文のスライドには、図・表・大きな数字・比較のどれかを必ず置く。5節「図の案」を「なし」にしない
- **中身の具体さ**：本文の半分以上の枚に、出典つきの数値・実際の場面の例・よくある間違いの例を入れる（2節の「図で見せるもの」「本文の要点」「青帯」で数える）。
  「〜を確認」「〜に注意」の言い換えだけの枚が続くと △

### 5. スライドと原稿を作る

設計メモを**講義録の代わり**にして、SKILL.md の手順3〜6（図 → ビルド → 描画確認 → 完成後レビュー → 原稿HTML）で作る。
手順3〜6は、SKILL.md「手順と担当」のとおり、空の会話から始めた【別のエージェント】（制作役と仕上げ役）に任せる（設計メモの場所と作業フォルダを渡す）。
講座では SKILL.md の手順0の質問は、講座を始めるときのヒアリング（手順1）で済んでいる。回ごとには聞かず、README の「学習者とゴール」（テーマへの詳しさ・学習者のプロフィール）を設計メモの1節に写す（丁寧さは詳しさから。回ごとに変えてよい）。
構成案は設計メモの2節がそのまま使え、レビューも済んでいるので、SKILL.md の手順2（outline.md・構成案レビュー・ユーザーの確認）は省く。
細かい決まりは references/steps.md の「講座の回を作るとき」節（`guide.py steps 講座の回`）。
スライド作りは、設計メモをスライドに起こすだけにする（事実は設計メモで確かめ済み）。渡し方：
- SKILL.md「手順と担当」のとおり、制作役1人に図と本文・原稿を、仕上げ役1人に組んで直す所から原稿HTMLまでを頼む（どちらも【別のエージェント】。モデルは指定しない）。
  依頼文は `brief.py 制作役 <work>`・`brief.py 仕上げ役 <work>` が作る（SKILL.md「手順と担当」）。設計メモにない事実は足さず、足したいときは理由を添えて返す
- サブエージェントの中から別のサブエージェントを起動できない環境では、サブエージェントには手順5（描画確認）までを頼み、
  完成後のレビュー（手順5b）は戻りを受けてこのセッションが起動する
- 設計メモにない説明（資料外の一般論）が要るときは、勝手に足さず、返答に書き、メインが設計の担当（新しく起動）に確かめさせる
- 図の下描きはレビュー待ちの間に始めてよい（レビューで図の直しが出ても小さい）
- 原稿は **AI講義モード**。書き方は references/steps.md「原稿のモード」の表のとおり（聞き手を「あなた」と呼ぶ、問いかけ、学習者の専門への橋渡し）
- 構成は「表紙＋本文＋確認問題→解答」。**「実際のやり取り」のスライドは最初は作らない**（まだやり取りがない）。
  ユーザーのコメント・答えへの回答は手順6の質問回答デッキで返す
- 設計メモの出典は、原稿の ※行に `※（出典）…` で残す（ユーザーは読まなくてよいが、確かめられるように）
- 出力：`<講座フォルダ>/0N_<題>_スライド.pptx`・`0N_<題>_原稿.html`（PDF は作らない）
- 渡す前に SKILL.md 手順7の確認（`check_done.py`）を走らせ、✘ が無いことを確かめる。サブエージェントに作らせたときも、戻りを受けてこのセッションで走らせる

### 6. コメント・答えを受けて、次の回へ

- ユーザーが「コメントした」と言ったら SKILL.md の手順8で質問回答デッキを作る。
  **回答の方針（`answers.md`：何がわからないか・答え・資料外の補足）は設計の担当が書く**（制作役には書かせない）（講座は資料が薄いことが多く、答えが設計メモの外に出やすい。
  事実の誤りがそのまま講座に入る）。`answers.md` ができたら、デッキの build・図・原稿・描画チェックは制作役と仕上げ役に渡してよい（手順5と同じ渡し方）
- 回答し終えたら、README の「つまずき一覧」に、誤解や抜けていた概念を1行ずつ足す（回・問題番号・何を取り違えたか）
- 次の回を作るときは、手順4の 7. でこの一覧と質問回答デッキを読んでから設計メモを書く
- **質問回答デッキも次の回も、新しい会話で始める**（SKILL.md「手順と担当」）。前の回の会話を続けると、その長い会話を操作のたびに読み直す。新しい会話は `next_step.py <講座フォルダ>` と README（地図・決め事・つまずき一覧）から再開できる
- 数回ごとに、つまずき一覧から**解き直し問題**（前の回の△×だった問題の言い換え）を確認問題に混ぜる（間隔をあけた復習）

## 判断に迷ったら

- 正確さを最優先。分からないことは書かないか「要確認」と書く。講師らしく断定したくなる所ほど裏を取る
- 学習者の背景への橋渡しは、正確に対応するものだけ（無理なたとえは使わない）
- 1回の分量を増やすより回を分ける。水増しもしない。ただし本文が10枚に届かないのは、たいてい話が抜けている（前提の説明・具体例・数値の例・つまずきやすい所・前後の回とのつながり）。
  地図の段階で回ごとの話を10枚ぶん見積もり、足りなければ回をまとめる。どうしても少なく（多く）なる回は、設計メモの2節に「枚数の理由：…」と書く（`check_memo.py` が見る）
