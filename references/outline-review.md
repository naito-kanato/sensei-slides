# 構成案のレビュー（サブエージェント）

構成案（`<work>/outline.md`）を、**本文・図・ビルドに進む前に**別のサブエージェントに評価させる。
自分で作った構成案は自分では粗が見えにくい。資料を自分で読んだ第三者の目で、流れ・抜け・図の選び方を点検する。

**レビュー担当は、構成案ができてから新しく起動する（先読みさせない）。** 先読みさせた担当は構成案ができるまで10〜20分待つので、そのあいだに会話がキャッシュから外れ、続きを頼んだときに資料を抱えた会話全体を書き直す代金がかかる。構成案ができてからの待ちが数分短くなる得より、こちらのほうが大きい。
担当は起動されたら資料を読み（A）、続けてレビューする（B）。

## 流れ

1. 構成案を作る側（【別のエージェント】が使える道具では設計の担当。SKILL.md「手順と担当」）が資料を読み、構成案（outline.md）を作る
2. 構成案ができたら、【別のエージェント】でレビュー担当を新しく起動する（`brief.py レビュー担当 <work>`。モデルは指定しない＝メインと同じ。SKILL.md「必ず守る」）。
   担当は下の「A. 資料の読み方」で資料を読み、続けて「B. レビューの依頼」の観点でレビューし、結果を outline_review.md（講座は memo_review.md）に書く。
   構成案を作った側は、レビュー担当の作業を自分でやり直さない
3. 構成案を作った側がレビューのファイルを読み、「必ず直す点」はすべて outline.md に反映する。「直すとよい点」は採否を自分で判断する
4. ユーザーに構成案を見せるとき、レビューの判定と、それを受けて直した点を2〜3行で添える
5. 大きく組み替えた場合だけ、同じ担当に「outline.md を更新したので再レビュー」と送ってよい（1回まで。使用量を抑えるため、小さな直しでは送らない）

## A. 資料の読み方（レビューの前に）

```
あなたはゼミ発表スライドの構成案をレビューする担当です。構成案はできています。
先に資料を読み、そのあと B の観点でレビューしてください。
ファイルは読むだけにしてください（レビューの結果のファイルだけは書く）。

- 資料: <資料PDFのパス>。担当範囲: <例: 3.2節 pp.40–48>
  ページ画像は <work>/src/pNN_L.png・pNN_R.png（見開きの左右）、論文ならテキストは <work>/src/pNN.txt。
  担当範囲の始まりと終わり（前後の節の混入）に注意。
- 判断基準（レビューで使う）: `python <skill>/scripts/guide.py style-guide 3`（3節と文字量の目安）と `guide.py figures 1`。論文紹介の発表のときだけ `guide.py style-guide 5` も（講座・輪読・研究発表では読まない）

やること: 担当範囲を全部読み、段落ごとの要点・式・数値・図を自分用にメモする（返答には書かない）。
読み終えたら、止まらずに B に進む。
```

## B. レビューの依頼（A のあと、同じ担当が続けて行う）

```
構成案ができました: <work>/outline.md
聞き手: 研究室のゼミ（物理系の学部生・院生）。発表時間: <分、不明なら「不明」>
ユーザーが決めていること: <例: 熱電対のスライドは回路図のまま。なければ「なし」>

先に読んだ資料と突き合わせて、次の観点で評価してください。
1. 流れ: 青帯（結論）の列だけを上から読んで話が通じるか。順序の入れ替えや、つなぎが必要な箇所。
   筋の表（状況・複雑化・問い・答え）の問いが前のほうで立ち、答えの枚で本当に答えているか。「前の枚から」の語と種類が実際の青帯のつながりと合っているか（「しかし（意外）」なのに予想が先に立っていない、「しかし（壁）」なのに壁が青帯に出ていない、など。references/story.md 2節）
   **入口と問い**：筋の状況が、聞き手が今知っていること・やっていることから始まっているか（年代の最初や資料の冒頭から入って、問いの前に知らない話が何枚も続いていないか）。問いが、筋の表で選んだ複雑化の型から本当に出てくる問いか（型だけ選んで、一文がその型の形になっていない・複雑化と問いがつながっていない、など）。問いの枚に、問いの一文がスライドにも載る案になっているか（原稿で言うだけになっていないか）。答えの枚が一覧の「答えの位置」どおりか（先＝問いのすぐ後で答えと柱の一覧、後＝後ろ3分の1で回収）。選んだ話の型（`話の型：…`）が筋に合っているか、型の拍の枚がその役（壁・意外・答えと柱…）を本当に果たしているか
2. 網羅と重複: 資料の段落・式・図のうち、どのスライドにも割り当たっていないもの／2枚に重複しているもの。
   **枚どうしの重なり**：青帯・言いたい教訓が同じ2枚（言い方や例が違っても、同じことを言っている。例：離れた2枚がどちらも「集団の結果は個人には当てはまらない」）。
   青帯の列を2枚ずつ比べて探し、1枚にまとめるか、片方を別の役（例 → 一般化、壁 → 答え、使い方）に変える案を書く
3. 1枚1メッセージ: 青帯が結論になっているか（見出しの言い換えや内容の要約になっていないか）。要点が4個を超えていないか
4. 図の選び方: その図が聞き手の理解を最も増やすか（テーマの視覚化か、難所の視覚化か）。もっと効く図があれば具体的に。図の案の目的（「比べる：棒グラフ：…」の「比べる」）が、その枚で伝えたいことに合っているか、種類がその目的に合っているか。
   推測の多い概略図になっていないか。**文字の箱を並べただけの図**や、数値を2つ以上比べる・割合・時間の変化を文字だけで書いた枚は、棒グラフ・折れ線・表・模式図にできないか
5. 正確さ: 青帯・要点が資料の記述と食い違っていないか。資料にない主張が混ざっていないか
6. 量と時間: 1枚の量（要点の数、文字量が100〜150字に収まりそうか）、全体の枚数と発表時間の釣り合い（1枚1.5〜2分）
7. 聞き手の難所: 聞き手がつまずきそうなのに、図や説明の手当てがない箇所

最後に、立場を変えてもう一度読んでください。
8. 推論距離の監査（聞き手の引っかかり）
   聞き手は outline.md 冒頭の「聞き手の前提知識」の人です（知っている／知らない が書いてある）。
   あなた自身の知識で穴を埋めないでください。「わかるか」ではなく、**この聞き手が、このスライドとそれより前のスライド
   （本文・図・原稿の列）に書いてあることだけで渡れるか**を試し、聞き手が自分で補う前提を、1つずつ文で書き出します。
   - **先に、名前を洗い出す**：各枚の本文・図のラベル・原稿に出る「知らない」側の名前（法則・式・記号・手法）を並べ、その枚かそれより前に中身の一言があるかを確かめてから穴を書く
   - 1枚を「図の読み方 → 見えたこと → 解釈 → 結論」などのつなぎ目に分ける。原稿の文から文への飛びもつなぎ目。穴の無いつなぎ目は書かない
   - **枚ごとの数はそろえない**。穴の無い枚は書かず、つなぎ目ごとに穴があれば1枚に何行でも書く（学習者が詰まった枚は、要が2つ以上あることが多い）。全部の枚に1つずつのようにそろったら、つなぎ目を試し直す
   - **種類**（1つ選ぶ）
     - 用語：「知らない」側の語・単位・略語・記号が定義されずに使われる。意味が一意に取れない言い回し（「緩和できる」）も用語
     - 出どころ：信号・量・現象が、何から・どんな過程で来るか（何をどう測る・どうやって起こる）が書かれていない
     - 論拠：見えたこと・前提から結論へ渡る理屈（なぜそうなるか、数値や図の意味）が書かれていない
     - 比較：何と比べているか（対照・基準・スケール）が書かれていない
     - 範囲：どこまで言えるか（定義の境界・因果・一般化・条件）が書かれていない、または言い過ぎ
     - 根拠：主張を支えるデータ・観測・定義の出典が無い
   - **要否**（要1〜要4と深の5つ全部について、当たるかを1つずつ答え、**当たるものを全部**「・」でつないで書く。例：`要1・要4`、`要3・深`。要どうし・要と深が重なってよい）
     - 要1：**この枚の結論（青帯）の「なぜ・どうやって」**がこの枚に無い（あとの枚で説明するなら、この枚に予告が無いかぎり要1。聞き手はこの枚で止まる）
     - 要2：**「知らない」側の、名前の付いた法則・式・用語・手法**が、中身なしに使われる（中身＝何を表すかの一言。「log τ が 1/T に比例する直線」のような見え方だけでは中身にならない。
       学習者は見え方が書いてあっても「アレニウス則ってなんだっけ」と止まった）。**種類を比較・論拠などで書きたくなっても、補う前提が名前の付いた語の中身なら要2にし、種類は用語にする**
     - 要3：この前提が無いと、**あとの枚（講座ならあとの回も）の結論・確認問題の答え・作り手の意図**が分からない。「使う所」に [番号] を書く（要1・要2・要4ならこの枚）。
       作り手の意図＝講座なら設計メモの「この回のゴール（言えるようになること）」と「橋渡し」（学習者の分野との対応づけ）、発表なら「青帯だけを上から読む」話の筋と、方針.md の「いちばん言いたい結論」。
       「使う所：ゴール2」「使う所：話の筋（背景→結論）」「使う所：橋渡し（〇〇との対応）」のように書く。**ゴール・話の筋・結論・橋渡しに書いてある言葉につながるときだけ**（書かれていない意図を想像しない）
       次の2つも要3に入れる：
       - **遠い前提**：使う前提が、使う枚から何枚も前か前の回にしか無く、使う枚に思い出させる一言が無い。補う前提の頭に「遠い（〇枚前・前の回）」と書く（何枚からを遠いとするかは、データで決めるまで数を決めない）
       - **呼び名の揺れ**：同じものを、あとの枚で別の名前（略号・記号・言い換え）で呼び、どこにも「＝」でつないでいない。使う所は別の名前で呼んだ枚
     - 要4：**動作・過程を表す語（動詞。切る・溶ける・つなぐ・凍結する・緩和する など）から、この聞き手が自分の分野の直感で思い浮かべる像と、ここで実際に起きていることが違う**のに、
       実際に何が起きるかが書かれていない（例：「ウイルスがパソコンに感染する」から、生き物がうつって増える像を思い浮かべるが、実際はプログラムが写されて動くだけ）。
       同じ語でも、聞き手の分野では別の操作を指すもの（物性の人にとっての「アニール」「緩和」など）もここ。補う前提の頭に「像：〇〇と思い浮かべる → 実際は△△」と書く。使う所はこの枚
     - 深：無くても結論は分かるが、知ると理解が深まる（背景・定義の慣習・出典・一般化・ほかの例・実務）。要に当たらなければ深だけ。要に当たっても深の性格もあれば両方書く。深だけの行の「使う所」は「なし」
     - 迷ったら、使う所を具体的に挙げられるかで決める
   - 各行に、自然に橋を架ける方法を1つ添える。説明を足すより、流れの中で済ませる方法を優先する：
     前のスライドで先に触れておく／「理由は次で」の予告／順序を入れ替える／本文の1句に括弧で添える／結果の後に「⇒ 何が言えるか」の1行／
     図の注記／原稿の1〜2文

結果は <work>/outline_review.md（講座は memo_review.md）に次の形で書き、返答には判定と「必ず直す点 N件・直すとよい点 N件」の1行だけを書く。
出力（日本語で簡潔に。この形式で）
- 判定: 「このまま進めてよい」または「直してから進める」
- 総評: 3行以内
- 必ず直す点: 番号つきで「[スライド番号] 問題 → 具体的な修正案（根拠：資料の頁）」
- 直すとよい点: 同じ形式
- 資料にあるのに構成案から抜けている内容: 頁と内容
- 推論距離: 穴1つを1行で、次の形だけで書く（スライド順。穴の無い枚は書かない）
  `[番号] 「A ⇒ B」｜種類｜要否（要1・要2・要3・要4・深 のうち当たるもの全部）｜補う前提：…｜使う所：…｜架け方：…`
  例：`[7] 「log τ が直線 ⇒ アレニウス則」｜用語｜要2｜補う前提：アレニウス則＝一定の山を越える熱活性化で τ∝exp(E/kT)｜使う所：7・14｜架け方：本文に括弧で一言を添える`
良い点の列挙や、構成案の書き写しは不要。指摘がない観点は書かなくてよい。
```

## 推論距離（聞き手の引っかかり）の扱い（メイン側）

過去の論文紹介では、完成後レビューを通ったあとでも、発表者本人が、単位・測定手法の名前・比べている相手・装置の役目・因果の範囲など7つを質問した。結果スライドが「AIなら理解できるが人だと詰まる」状態だった。
書き手（AI）は自分の知識でつなぎ目を埋めてしまう（知識の呪い）。AIのレビュー担当も同じなので、「わかるか」ではなく
**補う前提を1文ずつ書き出させ、種類と要否を付けさせる**（数はスクリプトが数える）。構成案の段階で拾い、話の流れに織り込む。

**用語と考え方**：推論距離（inferential distance）＝結論までに聞き手が自分で補う前提の数。書かれていない前提を持つ論証は
省略三段論法（enthymeme）、文の間を読み手が補う推論は橋渡し推論（bridging inference）と呼ばれる。
種類は、論証の要素（トゥールミンの主張・根拠・論拠・限定）に、用語・出どころ・比較を足したもの。
予備知識の少ない読み手ほど、つながりを明示した文章でよく理解し、詳しい読み手には明示しすぎが逆効果になる（結束性の研究・熟達化の逆転効果）。丁寧さは聞き手に合わせて調整する量。

**要3の範囲を広げたときの確かめ**（同じ講座の材料で、レビュー役2人ずつ、コメントは見せずに）：作り手の意図（ゴール・話の筋・橋渡し）・遠い前提・呼び名の揺れを足しても、
深まりが要3に化けることは増えず、学習者が詰まった「前の回で出た語」（遠い前提）を新たに拾えた。「聞き手の素朴な思い込みを打ち消す一言が無い」も試したが、
狙った2件は拾えず要3が増えたので入れていない。

**要4と複数選択を足したときの確かめ**（同じ材料、レビュー役2人ずつ）：学習者が「どうやって切るの」と詰まった枚（聞き手は原子の模式図で、結合を物理的なつながりと読んでいた）を、
前の決まりでは2人に1人しか拾えなかったが、要4 で2人とも拾えた。ほかにも、聞き手の分野で別の操作を指す語（アニール・緩和）や、別の像を持つ語（発散・凍結）が出た。
要の行は増えるが、増えた分の多くは「要と深の両方」の行で、これを数えなければ、コメントの無い枚の要は前とほぼ同じ。要4 は詰まった1件を見てから作った決まりなので、次の講座のコメントで確かめ直す。

**要と深**（実際の講座で、学習者が詰まった所とそうでない所で合わせた。数で詰まった枚を拾えるのは「要」だけで、段数のような大きさは AI では分かれなかった）
- **要**だけを推論距離に数え、手当てを必ず考える。学習者が実際に止まった所は、ほぼ全部が「この枚の結論のなぜ・どうやって」
  「名前の付いた知らない法則・用語」「あとで使う前提」「動作の語の像のずれ」のどれかだった
- **深**は数えない。手当ての検査にも入れない。講座なら原稿の ※ に1〜2文で入れてよい候補、質問が来たときの回答の材料として残す
- **要と深の両方が付いた行は「迷い」**：手当ての検査には数えない（`check_outline.py` は一覧に出すだけ）。メイン側が、その枚の結論に要るかで採否を決める

**構成案の冒頭に書く2行**（メイン側が作り、レビューの前提にする。ユーザーが直してよい）
- `聞き手の前提知識：知っている＝…／知らない＝…`（例：知っている＝波と干渉・周波数・太陽質量・正規分布と σ、
  知らない＝ひずみ h・SN 比・チャープ質量・誤報率）。「知っている」側の用語と事実は穴に数えない
- `丁寧さ：1`（1枚に許す「要3」の数。要3は、あとの枚・確認問題・回のゴールや話の筋で使う前提）。聞き手のテーマへの詳しさから決める：初学者 0（要は全部架ける）／多少知っている 1／かなり知っている 2。
  **要1（この枚の結論のなぜ）・要2（名前の付いた知らない語）・要4（動作の語の像のずれ）は、丁寧さによらず必ず架ける**（この枚で止まる穴なので）。丁寧さで許すのは、あとで止まる要3だけ
  （詳しい聞き手は、あとで自分で組み立て直せることがある）。名前の付いた語は、初出で一度中身を言えば以後は穴でない。1枚に新しく出る名前は2個まで
- 前提知識の「知っている」には、聞き手がふだん使っているものだけを書く。**習ったが自分の専門では使わない法則**（物性物理の人にとってのアレニウス則など）は「知らない」側に入れる

**書くときから避ける**（構成案・設計メモの表、build.py の本文、notes.md の原稿を書くとき。レビューで見つかる穴を減らす）
- その枚の結論の「なぜ・どうやって」を、その枚に書く。次の枚で説明するなら「理由は次で」と予告する
- 「知らない」側の名前の付いた法則・式・用語・手法は、初出で何を表すかの一言を添える（本文の括弧か原稿。見え方・式の形だけでなく意味を）
- 動作・過程の語（切る・凍結する・緩和する など）は、聞き手の分野の直感と違う中身なら、実際に何が起きるかを一言添える（「切る＝橋の酸素を端の酸素に変える」のように）
- 数値には比べる物差しを、「変化なし」には「⇒ 何が言えるか」を、測った量には何をどう測ったかを添える
- 結論は、その図・データから言える範囲で言い切る（因果・一般化を強めない）

0. **レビュー担当が返した結果を、そのまま `<work>/outline_review.md` に残す**。推論距離は穴1つを1行で、
   `[番号] 「A ⇒ B」｜種類｜要否｜補う前提：…｜使う所：…｜架け方：…` の形（見本は `examples/zemi/outline_review.md`）
1. レビューの「推論距離」から、**妥当なものを選ぶ**
   - 採る：要1・要2・要4の全部、丁寧さを超えた要3（1枚に要3が丁寧さより多い枚の要3）、結論の読み方が変わるもの（対照の意味、因果の範囲）
   - 採らない：資料にも答えのない細部、話の筋に関係しない豆知識、「知っている」側のはずのこと（前提知識の行が違うなら行を直す）。「深」は手当てに書かなくてよい
   - 迷い（要と深の両方の行）：その枚の結論に要るなら採る。要らなければ深と同じ（原稿の ※ の候補）
2. **構成案を更新する**。説明を別に足すのではなく、流れの中で答えが出るようにする
   - 前提が要るなら、その前のスライドで先に触れる（順序の入れ替え・前のスライドの本文に1句）。あとで説明するなら予告の一言
   - 「変化なし」の結果には「⇒ 何が言えるか」の1行を本文に入れる
   - 単位の換算・略語の意味は、初出の本文に括弧で添える（「100〜500 mbar（0.1〜0.5 気圧）」）
   - 本文の文字量（100〜150字）を超えるなら原稿の1〜2文に回す。スライドを増やすのは、前提が1枚分ある場合だけ
3. outline.md の表を直し、表の下に `## 引っかかりへの手当て` を足す。採ったものを「穴 → どのスライドで・どう架けたか」で1行ずつ、
   採らなかったものは理由を一言添えて残す（完成後レビューと原稿を書くときに見返す）。**各行は `- [スライド番号]` で始める**
   （`check_outline.py` が、手当ての要る枚（要1・要2・要4がある枚と、要3が丁寧さより多い枚。迷いの行は数えない）が全部載っているかを [番号] で突き合わせる）
4. ユーザーに構成案を見せるときは、前提知識と丁寧さの2行と、採った穴を2〜3個だけ添える

## 判断のしかた（メイン側）

- 「正確さ」「網羅」の指摘は、必ず自分でも資料の該当頁を見て確かめてから直す（レビュー担当の読み違いもありうる）
- 図の提案は figures.md 1節の基準（理解が最も増えるもの、推測の多い概略図は避ける）で採否を決める
- ユーザーがすでに決めたことは、レビューで別案が出ても覆さない
